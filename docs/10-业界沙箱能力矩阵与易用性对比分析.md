# 10 · 业界开源沙箱能力矩阵与易用性对比分析

> 调研日期：2026-11-17 · 目的：把 aisbx 的**设计取舍**放到业界坐标系里，回答三个问题：
> ①同类工具各自「能做什么、靠什么机制做」；②「怎么用、好不好用」；③aisbx 的差异化与差距分别在哪。
>
> 本文是 `docs/05`（三家 coding agent 竞品调研）的横向扩展：那篇聚焦 Claude Code/Codex/dsh
> 三个**同形态产品**，本篇扩展到 OS 原语、进程沙箱、容器/微 VM、Agent 沙箱平台、Wasm 运行时五类。
> 说明：**能力矩阵描述的是公开资料与默认配置下的能力**，不承诺各工具在特殊配置下的上限；
> 凡涉及 aisbx 的能力值均取自本机 `aisbx capabilities --json` 的真实输出与三平台 CI 断言。

---

## 0. 结论速览

1. **aisbx 的差异化不在「隔离得多严」，而在「隔离之后怎么把权限还回去」**。业界多数工具的授权是
   「预配置静态规则」或「拒绝后以更宽策略重跑」，aisbx 把「精确感知 → 一次性 token → 策略快照重跑」
   做成了**跨三平台同构的对外契约**（`status.pending[]` / `retry` / `precision` / `attributed`），
   这是 srt/Codex/dsh 都未产品化的能力（`docs/05` §3 已验证）。
2. **隔离强度上 aisbx 属于「共享内核的进程级沙箱」**：与 bubblewrap/Firejail/srt/Codex 同一档，
   弱于 gVisor（用户态内核）、Kata/Firecracker（独立内核微 VM）和 E2B（Firecracker + 快照）。
   选 aisbx 的前提是信任宿主内核、追求毫秒级启动与零管理员部署。
3. **易用性是 aisbx 的明显短板**：CLI 有 6 个子命令、策略 JSON 有 5 个嵌套段、无 profile 生态、
   无 SDK、无快照；相比 Firejail 的 `firejail firefox`（一条命令）和 E2B 的
   `Sandbox().run_code(...)`（一行 Python），接入门槛高一个数量级。
4. **能力报告 + fail-closed 是 aisbx 对齐业界最佳实践的部分**：`--require-full` 对应 Codex 的
   `RulesetStatus::NotEnforced` 与 dsh 的 `SANDBOX_UNAVAILABLE`，比 Firejail/bubblewrap 的
   「失败后可能裸跑」更可信；但 aisbx 的资源限制在 macOS 全为 `unavailable`，这部分不如
   Windows Job 完整。
5. **感知精度是分水岭**：只有 macOS 有内核日志通道（L2，`precision=exact`）；Linux/Windows
   文件越界只能靠程序 stderr 自报（`reported`，可伪造）。这与 srt/Codex/dsh 的限制一致，
   但 aisbx 是少数把「精度」和「归属」作为**结构化字段暴露给 agent** 的工具。

## 1. 调研范围与方法

### 1.1 五类工具

| 层 | 代表工具 | 信任边界 | 本文代号 |
|---|---|---|---|
| L0 OS 原语 | Landlock、seccomp-bpf、Seatbelt（sandbox-exec）、AppContainer + Job Object + ACL | 内核 syscall / LSM | 原语 |
| L1 进程沙箱 | bubblewrap、Firejail、nsjail、**srt（Claude Code）**、**Codex linux-sandbox**、**dsh landlock-run** | 同宿主的另一个进程 | 进程 |

### 2.2 三个关键维度的深读

#### 维度 A：隔离强度与信任边界

- **共享内核档**：aisbx / srt / Codex / dsh / bubblewrap 都依赖宿主内核的正确性。
  srt 特别用第二层 seccomp 禁 `unshare`/`mount`/`setns`/`umount2`/`pivot_root`/`clone3` 来堵
  bubblewrap 只读 bind 被沙箱内自建 userns 拆除的逃逸（`docs/05` §2.1）。
  **aisbx 当前在 Linux 上把 Landlock/seccomp 标 `partial`，未做同等的反逃逸 seccomp 过滤器**——
  这是明确的安全差距，不是文档措辞问题。
- **用户态内核档**：gVisor 用 Sentry 拦截约 250 个 syscall，牺牲部分兼容性换 syscall 边界隔离；
  适合不可信代码，但 I/O 开销 5-15%。
- **微 VM 档**：Kata/Firecracker 启动 100-200ms、内存 20-50MB 起，隔离强度最高；
  Firecracker 要求 KVM，Linux-only，且不是开箱即用的容器替代。
- **Wasm 档**：WASI 没有 `open()`/`socket()` 这类 ambient authority，能力由 host 显式注入，
  安全模型最干净；代价是必须把程序编译成 Wasm，且系统 API 覆盖有限。

**aisbx 的取舍**：选择 L1 是为了「同一二进制在三平台跑同一份策略」，把复杂度放在
**平台后端适配 + 授权协议**上，而不是追求比肩微 VM 的隔离强度。这个取舍对「本地 agent
执行用户自己的代码」是合理的，对「运行完全不可信的多租户代码」则不够。

#### 维度 B：运行时授权——aisbx 的真正差异点

| 工具 | 拒绝后怎么办 | 授权粒度 | 是否需要重启命令 | agent 可否编程式授权 |
|---|---|---|---|---|
| **aisbx** | 上报 `pending[]` → 宿主签 token → 并入快照 | 单文件/单 host:port | **是(文件)** / 否(网络) | ✅ `status`+`authorize` |
| srt | ask callback 问用户，下一次连接生效 | host:port | 网络不需要 | ✅ `--control-fd` |
| Codex | agent 层审批，以更宽策略**重新执行** | 策略档位 | 是 | ⚠️ agent 侧实现 |
| dsh | 同 Codex，且要求新策略严格更宽 | 策略档位 | 是 | ⚠️ `ctx.approval` seam |
| Firejail/bwrap | 无授权机制，只能改配置重跑 | 静态 | 是 | ❌ |
| E2B | SDK 层自行决定 | 由平台 API 决定 | 视实现 | ✅ |
| WASI | 启动时注入 capability | preopened dir / host | 必须重建实例 | ✅ 宿主代码 |

**aisbx 的「重跑」与竞品的「重跑」有实质区别**：aisbx 把重跑做进 launcher
（`launcher_retry: full`），agent 只需 `status` → `authorize` 两次调用；Codex/dsh 的重跑
在 agent 层，需要 agent 自己保存 argv、重建执行。aisbx 还额外保证**授权粒度不外溢**
（T13：只给目标文件权限，同目录既有文件仍不可写），这是简单「换更宽策略重跑」做不到的。

#### 维度 C：可观测性与归因

aisbx 把感知通道分成三层并**结构化标注**：

| 通道 | 来源 | 精度 | 归属 | 平台 |
|---|---|---|---|---|
| L1 | 程序 stderr 自报 | `reported` | 确定 | 三平台 |
| L2 | 内核 violation 日志 | `exact` | 两级判定(PID 集合+进程组) | 仅 macOS |
| L3 | HTTP CONNECT/SOCKS5 代理 | `exact` | 确定 | 三平台 |

竞品中只有 srt 有可比的 `SandboxViolationStore` + 128bit `commandId`；Codex 靠 stderr
特征匹配（`"Operation not permitted"`），dsh 靠 session log。**aisbx 的 `precision` /
`attributed` 字段让 agent 能判断「这个路径该不该拿去问用户」**，这是面向 agent 的设计，
而非面向人的日志设计。

## 3. 使用方式对比（易用性）

### 3.1 各工具的「第一行代码」

| 工具 | 最小使用示例 | 前置条件 | 学习曲线 |
|---|---|---|---|
| Firejail | `firejail firefox` | 安装 + setuid | 低（1000+ 现成 profile） |
| bubblewrap | `bwrap --ro-bind / / --bind $PWD $PWD --unshare-net bash` | 安装 bwrap，理解 bind 语义 | 中 |
| Landlock | Rust 代码调用 `landlock::Ruleset::new().handle_access(...).restrict_self()` | 改程序源码，内核 ≥5.13 | 中（需重编译） |
| srt | `srt <cmd>` / TS `new SandboxManager(opts).run(cmd)` | Node + bwrap/socat/ripgrep；Win 需 UAC 安装 | 中 |
| Codex | agent 内部自动调用，用户只配 `sandbox_mode` | 使用 Codex CLI | 低（但不可单独复用沙箱） |
| dsh | `ctx.sandbox.confine(argv, policy)` | 使用 dsh harness | 中（插件式） |
| gVisor | `docker run --runtime=runsc ...` | 安装 runsc，切换 containerd runtime | 中 |
| Kata | `kubectl` 指定 runtimeClass | K8s + KVM | 高 |
| Firecracker | HTTP API 配置 VM/Drive/Network 后 `InstanceStart` | KVM + 集成工作 | 高 |
| E2B | `sbx = Sandbox(); sbx.run_code("...")`；模板用 Dockerfile | 账号/API key/网络 | 低（SDK 友好） |
| Wasmtime | `WasiCtxBuilder::new().preopened_dir(...)` + `linker` | 把程序编译成 Wasm | 中高（生态限制） |
| **aisbx** | `aisbx run -p policy.json -- <cmd>` + agent 侧 `status`/`authorize` 循环 | Rust 构建 + bwrap(Linux) 或系统 sandbox-exec(macOS) | **中高（见下）** |

### 3.2 aisbx 的易用性画像

**优点**

- 单一二进制，无守护进程；Windows 无需管理员（AppContainer 路径优于 srt 的 UAC 安装）。
- 命令语义稳定：`run` / `escalate` / `authorize` / `status` / `capabilities` / `policy-check`。
- `--json` 事件流 + `status.pending[]` 是**为 agent 编程消费设计的**，不是给人看的日志。
- 三平台同形：`contract_check.py` 用同一份基线检查 19 项，能力差异结构化暴露而非静默降级。
- 有大量可直接复制的实测手册（`docs/09` §0-14）与三平台冒烟脚本。

**成本**

- **策略 JSON 有认知负担**：`filesystem` / `network` / `resources` / `broker` / `escalation`
  五段，且 `escalation` 三模式（`prompt`/`auto`/`deny`）的裁决顺序需要理解
  （黑名单前置 > token > 模式）。
- **授权循环要 agent 自己编排**：`run` 后台启动 → `status` 轮询 → `authorize` → `wait`，
  虽然 launcher 会自动重跑，但 agent 必须管理进程生命周期。
- **无 profile 生态**：Firejail 有 1000+ 现成 profile，aisbx 每个任务都要写策略。
- **无 SDK**：只有 CLI 和 JSON，没有 Python/TS/Rust 客户端库；E2B 的 `Sandbox()` 一行调用体验明显更好。
- **无快照/暂停**：E2B 可 pause/resume 保存内存状态，aisbx 每次都是全新进程。
- **错误信息依赖程序生态**：Linux/Windows 的文件越界路径靠 stderr 自报，Rust/Go 程序
  只抛 `errno` 不带路径时，感知会退化（L1 覆盖率问题，`docs/03` §1.2 已登记）。

### 3.3 易用性评分（主观，5 分制）

| 维度 | aisbx | Firejail | bubblewrap | srt | E2B | WASI |
|---|---|---|---|---|---|---|
| 首次上手 | 2 | 5 | 3 | 3 | 5 | 2 |
| 日常单次使用 | 3 | 5 | 3 | 4 | 5 | 3 |
| agent 集成 | 4 | 1 | 2 | 4 | 5 | 3 |
| 策略表达力 | 4 | 3 | 3 | 4 | 4 | 5 |
| 可观测/调试 | 4 | 2 | 1 | 4 | 4 | 2 |
| 跨平台一致性 | 5 | 1 | 1 | 3 | 5 | 5 |
| 生态/文档 | 2 | 4 | 4 | 3 | 4 | 4 |
| **综合** | **3.4** | **3.4** | **2.4** | **3.7** | **4.7** | **3.3** |

> aisbx 的强项集中在「agent 集成 / 可观测 / 跨平台一致性」，弱项集中在「首次上手 / 生态」。
> 这与其设计目标一致：它是给 agent 框架接的底座，不是给终端用户直接用的包装器。

## 4. aisbx 与业界方案的差距清单

按「是否影响正确性/安全性」排序：

| # | 差距 | 对比对象 | 影响 | 建议 |
|---|---|---|---|---|
| G1 | Linux 未做反逃逸 seccomp（禁 userns/mount/setns） | srt `vendor/seccomp-src` | **安全**：bwrap 只读 bind 可被沙箱内拆除 | 按 `docs/05` M1 补第二个 helper（multicall），CI 加「unshare 必须失败」断言 |
| G2 | Linux/Windows 文件越界路径只能 `reported` | macOS L2 / WASI 天然 exact | **功能**：Rust/Go 程序不带路径时无法感知 | 接受为平台限制并如实标注（已做）；可选补 Linux fanotify（需特权） |
| G3 | macOS 资源限制全 `unavailable` | Windows Job 完整 | **功能**：macOS 上无法限内存/CPU/进程数 | 如实标注已做；不强行找等价机制（macOS 确实没有进程组级 cgroup） |
| G4 | 无 SDK / profile 生态 | E2B SDK、Firejail profiles | **易用性**：接入成本高 | 优先补一个薄 Python/TS 客户端封装 `status`+`authorize` 循环 |
| G5 | 无快照/暂停 | E2B pause/resume | **场景**：无法做长任务恢复/分叉 | 与 aisbx「一次命令一次沙箱」定位冲突，暂不做 |
| G6 | 策略无 deny glob / profile 继承 | srt deny-glob、Firejail profile | **易用性**：重复策略难维护 | 在 `aisbx-policy` 层加 include/继承（不破坏 `deny_unknown_fields`） |
| G7 | 网络授权无 resolved-address check | srt（拒 loopback/私网/云元数据） | **安全**：DNS rebinding 风险 | 已有 SSRF 拒绝 loopback（T9d），需扩展到私网/云元数据/IPv4-mapped |
| G8 | 审计无 `command_id` 128bit 归因 | srt `SandboxViolationStore` | **功能**：长命令串台风险 | 当前用 task 名隔离，足够单任务；多任务并发审计时需补 |

**aisbx 相对业界的优势**（应继续保留）：

1. **三平台同形契约**：`capabilities` 键集合严格相等 + 19 项跨平台契约检查，业界无同等做法。
2. **授权粒度不外溢**：单文件/单 host:port，T13 有实测断言。
3. **结构化降级**：`full/partial/unavailable` + `--require-full`，比「静默裸跑」可信。
4. **感知精度/归属显式化**：`precision` + `attributed` 让 agent 知道该不该信这个路径。
5. **无需管理员的三平台部署**：Windows AppContainer 路径优于 srt 的 UAC 一次性安装。

---

## 5. 选型建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 本地 agent 执行用户代码，需三平台一致体验 + 运行时授权 | **aisbx** | 唯一把授权协议做成三平台同形契约的方案 |
| 桌面应用快速加固 | Firejail | 一条命令 + 现成 profile |
| Linux-only，想自限且改得了源码 | Landlock | 非特权、内核原生、无 setuid 风险 |
| 需要比肩容器的隔离但保持 OCI 生态 | gVisor | syscall 边界隔离，`--runtime=runsc` 即接 |
| 多租户/完全不可信代码 | Kata / Firecracker / E2B | 独立内核，隔离强度最高 |
| 插件系统 / 受限 DSL 执行 | WASI + Wasmtime | 无 ambient authority，能力模型最干净 |
| 远程 agent 沙箱 + 快照 / 分支 | E2B | pause/resume + SDK + 模板生态 |

**对 aisbx 自身的建议优先级**：G1（安全）> G7（安全）> G4（易用性）> G6（易用性）>
G2/G3（如实标注已足够）> G5/G8（暂缓）。
