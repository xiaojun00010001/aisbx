## 0. 口径

| 概念 | 定义 |
|---|---|
| **真实系统测试** | 在对应 OS 的真实内核上执行 `aisbx run` 并断言可观测结果。CI runner 是虚拟化的**真实 OS**（AppContainer / Job / bwrap netns / Seatbelt / 统一日志均真实生效），不是 mock、不是交叉编译 |
| **仅编译检查** | `cargo check --target ...`，只证明能编译，不证明行为 |
| **WARN 跳过** | 能力报告判定该平台不具备该机制，按设计跳过，**不算通过** |
| **未测** | 既无断言、也无能力标记能覆盖；不能声称验证过 |

执行入口：`scripts/smoke.ps1`（Windows）、`scripts/smoke-unix.sh`（Linux / macOS）。
CI：`windows-smoke`（`windows-latest`）、`cross-platform-smoke`（`ubuntu-latest` + `macos-latest` + `windows-check`）。

### 仍未覆盖的边界（如实列出）

- **token 边界**：TTL 过期实际消费、跨任务挪用、`write` token 满足 `read` / `read` token 不满足 `write` 的方向校验、目录 token 覆盖子树。
- **重跑约束**：预算不随 attempt 重置、`MAX_ATTEMPTS=3` 上限、重跑副作用提示、新策略严格宽于旧且不超过批准范围。
- **路径攻击面**：符号链接 / TOCTOU / 硬链接别名 / 路径规范化双写（`real_path` vs `compare_key`）。
- **并发细节**：并发 `authorize`、同一任务多连接、审计重复写去重。
- **模式与 TTY**：`prompt` 同意、`stdin` 非 TTY fail-closed（`auto` 前缀放行已由 T10a 覆盖）。
- **资源**：C13 / C14 / C16 未实现；C19 仅 Windows 验证，Unix 宿主被 SIGKILL 时无进程树清理（`partial`，已知缺口）；C20 已修并断言。
- **Windows 文件侧差异**：Unix 的 `handle_control` 有 `has_real_violation`（必须真实撞过墙才能签发文件 token）；Windows 文件侧**没有**该校验（网络侧 `net-issue` 有）。控制管道 DACL 已排除沙箱，风险有限，但契约不对等，未擅自改动以免破坏既有 in-place token 流程。

### 4.3 第三、四轮：归属精度 + L1 通道 + status 契约（2026-11-08 ~ 11-09）

这一轮的重点不是堆功能，而是**把已有能力变得可被 agent 消费**，并补齐三平台的能力对齐。

Unix 侧新增断言：

| 断言 | 覆盖的缺口 |
|---|---|
| T7f 短命深层进程**不**作为越界上报 | 内核日志里混着同机其它应用的违规（实测 Chrome / `wifip2pd`）。未能归属的条目若当成越界，会去要用户授权无关路径 → 真实越权面 |
| T7g 未归属条目仍留审计记录 | 「不作为越界」≠「不记录」：路径仍需可见，供诊断 |
| T7i 存活的深层进程按**进程组**精确归属 | 内核上报的是**真正执行违规的那个进程**的 PID，可比入口深 3 层；按入口 PID 过滤必漏 |
| T7j 越界路径标注为内核来源且精确 | 路径精度需结构化标注（`exact`/`reported`），供 agent 决定如何呈现 |
| T7k 可归属的越界不重复出现在未归属列表 | 去重正确性 |
| T7l 未归属条目**不得**用于申请授权 | 防「拿他人违规骗过 token 签发」 |
| T11a 越界路径被采集（内核日志或 stderr 自报） | 补上 Linux/Windows 的文件侧感知（原为 `unavailable`） |
| T11b 越界路径精度已标注 | `precision` 字段 |
| T11c 无内核通道时精度如实为 `reported` | 能力报告不许虚报 |
| T14a status 给出待授权的**具体路径** | 原 status 只给数量 → agent 根本没法问用户 |
| T14b status 标注路径精度与归属 | 同上 |
| T14c status 报告 `needs_approval` 标志 | agent 需要知道「是否正在等授权」 |
| T15a 内核通道采到**真实**被拒路径（`exact`） | L2 是否受程序欺骗 |
| T15b 自称路径仅由 stderr 自报（`reported`） | 两个通道的可信度差异 |
| T15c 授权自称路径后**真实路径仍被拒** | 「L1 路径可伪造」是否构成越权——核心安全结论 |

Windows 侧新增（`smoke.ps1`，**只做了交叉编译，真机待 CI**）：

| 断言 | 覆盖的缺口 |
|---|---|
| T11a–T11d stderr 自报路径（L1） | Windows 原 `auto_violation_capture: unavailable` |
| T12a–T12c B 契约重跑闭环 | 原 `launcher_retry: unavailable` → 授权后 agent 重跑仍被拒（token 跨 run 不延续）→ 死循环 |
| T13a–T13c 授权粒度不外溢 | 授权「创建文件 X」曾对父目录授 Modify → 实际可改/删该目录下所有文件 |

配套单测从 4 项增到 **20 项**（stderr 解析含 Windows 路径形态 5 项、进程组归属 3 项、
未归属降级与 pgid 反查 3 项等），`aisbx-policy` 8 项不变。

### 4.5 第五轮：三平台真机端到端（2026-11-10，全部改动由 GitHub Actions 驱动）

本轮把「三平台真机测试」整体搬进 workflow，并由此暴露并修掉一批**只有真机才看得见**的问题。

**流程侧的 6 处改造**（元问题，不修则一次失败什么都拿不到）：

1. `aisbx` crate 的单测**从未进 CI**（只跑了 `-p aisbx-policy`）→ 改 `cargo test --workspace`
2. `rust-toolchain.toml` 让 rustup 装 minimal profile → **不含 rustfmt/clippy** → 三个平台齐刷刷红在 Format check → 显式声明 `components`
3. **门禁排在冒烟前面** → 门禁一红就把冒烟全挡住 → 改为「冒烟前置、门禁后置」
4. 结果**回写仓库**（`ci/runs/*`）→ 不再受 GitHub API 未认证配额（60 次/小时）限制
5. 回写并发竞争（三个 job + 15 次进度 push 抢同一分支 → rebase 冲突 → 结果被挤掉）→ **每 job 独立分支**
6. `git pull --rebase` 冲突时 git 会**进入交互等待** → CI 里就是永久卡死（Windows 冒烟曾连续三轮「60 分钟 timeout 也跑不完」，而它其实 2 分 09 秒就跑完了）→ 全程非交互

**产品侧修掉 14 个问题**，其中只有真机才暴露的：

| 平台 | 问题 | 性质 |
|---|---|---|
| 三平台 | 能力报告键集合三平台不一致（差 6 个）→ agent 只能靠「键不存在」去猜 | **交互不一致** |
| 三平台 | `aisbx` crate 单测从未进 CI | CI 缺口 |
| Windows | `grant_path_precise` 改签名后**漏改第三处调用点** → 编译失败 | 真 bug |
| Windows | 授权「尚不存在的文件」→ 授父目录 `AD` → 新文件继承的 ACE 没有写权限 → **先建后写必失败** | 真回归（此前引入） |
| Windows | `emit` 只 println 不落审计 → retry 事件从不出现在审计里 | 平台不一致 |
| Windows | `status_client` 用 `ReadFile` 阻塞读、**无超时** | 潜在挂死 |
| Linux | bwrap 只 bind **目录** + bind 源路径必须存在 → 授权「正要创建的文件」绑不上 → 授权形同虚设 | **平台不一致** |
| Linux | bwrap 白名单外目录只读 → 新建文件是 **EROFS** 而非 EACCES → L1 语义词表漏了它 | 真 bug |
| Linux | macOS 内核通道专用的代码在 Linux 上是 dead_code | 平台差异 |
| Linux | `pgid_table` 有两份定义，只给 macOS 版加了豁免 | 平台差异 |
| macOS | L1 噪声过滤把 `/var/folders/` 整目录当噪声 → 用户真实目标采不到 | 真 bug |
| — | 契约检查当场抓到「给 macOS 喂了 Linux 的期望值」 | 交互不一致 |

**补齐的场景**（平台无关的核心契约，原先一边有一边没有）：

- Unix 侧：`T11d` 路径正确、**`T12` B 契约「授权后重跑」**、**`T13` 授权粒度不外溢**
- Windows 侧：**`T14` status 交互**、**`T15` 对抗（伪造路径不构成越权）**

> 补齐后 Ubuntu 立刻红出 3 项，且是**真 bug**（bwrap 侧「授权后仍写不进」）。
> **这就是「覆盖所有场景」的价值**：这些场景之前在 Unix 侧根本没被测过。
> 修法与 Windows 侧**完全同一套语义**（宿主预创建空占位文件 + 单文件 bind +
> 结束时回收空占位文件）—— 三平台的授权语义由此对齐。

**Windows 冒烟仍缺一块**：T15a（对抗用例采不到自称路径）与契约检查失败。
契约检查的失败详情现在会随结果回写（`ci/runs/contract-<platform>.md`），下一轮即可定位。

### 6.1 分层：本地只做「秒级能发现的」，真机全部交给 workflow

| 层 | 内容 | 耗时 | 覆盖不到的 |

## 5. 结论

**「所有场景在对应系统的真实测试」仍未完成。** 已完成的是：
三平台各自的主链路与**统一的重跑闭环**（Windows 的 `launcher_retry` 本轮由
`unavailable` 补到 `full`）、P0 网络精确感知与运行中授权、macOS P1 文件精确感知、
三平台 L1 感知通道、统一 `status` 契约（agent 可据此问用户）、
以及 T9（fail-closed / SSRF / 并发隔离 / `--require-full`）、T10（能力契约组）、
T7f–T7l（归属判定与越权面）、T11–T14（感知通道 / 重跑 / 授权粒度 / status 契约）四轮断言。

C07 的 `prompt` / 非 TTY、C13 全任务内存、C14 CPU、C16 磁盘 IOPS（未实现）、
Unix 侧 C19 的 `partial` 缺口、C22 其余字段、token 边界、路径攻击面、
重跑约束、环境矩阵仍是明确缺口。
**CI 全绿只证明上表打 ✅ 的项，不证明其余项。**
