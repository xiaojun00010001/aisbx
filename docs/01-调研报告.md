# 调研报告:基于 AppContainer + Job Object 的本地沙箱产品

调研日期:2026-11-05。调研目标:是否存在把 Windows AppContainer / LowBox token 与 Job Object 组合成「面向 agent 的本地进程沙箱」的可用产品。

## 1. 对象清单与实现框架

### 1.1 landstrip(开源,Rust,最接近)

- 仓库 `landstrip/landstrip`(Rust + npm 包装,双许可证 Apache-2.0 / LGPL-2.1)。
- 跨平台:Linux=Landlock+seccomp broker,macOS=Seatbelt,**Windows=每次 run 创建 LPAC AppContainer**。
- Windows 实现要点:
  - per-run AppContainer profile,把 profile SID 授予 read/write 根目录 ACL,**进程树退出后自动移除 ACL**;
  - Job Object(KILL_ON_JOB_CLOSE)管理进程树,launcher 退出统一终止;
  - 网络零 capability 默认全拒;`allowNetwork: true` 时授予 internet + privateNetwork 两个 capability——**Windows 上 TCP 只有全开/全关两档**;
  - 明确否决 WFP 细粒度方案(需要提权,违背"非特权运行时"设计目标)。
- 策略格式 = Anthropic Sandbox Runtime JSON 子集(allowRead/allowWrite/denyRead/network.allowNetwork)。
- 可选加固:disableWin32k / disableExtensionPoints / strictHandleChecks / imageLoad 系列 mitigation。
- **没有提权/broker**:设计原则明确拒绝提权;Linux 侧有 seccomp broker 只做拒绝事件上报与 Unix socket allowlist。

### 1.2 OpenAI Codex Windows 沙箱(2026-05 工程说明,实验性)

- 事实背景:2025 年 9 月前 Codex 在 Windows 无沙箱,只能 WSL2 或裸跑。
- 第三方分析存在分歧:
  - 一派(基于 OpenAI 工程说明转述)称最终设计**弃用 AppContainer**,改用 restricted token + **synthetic SID + write-restricted token** + 专用沙箱用户 + 防火墙规则 + command-runner,全程无需管理员;
  - 另一派(评论文章)读作 AppContainer + WFP 内核过滤路线。
  - 共同点(可信度较高):文件写入边界 + 网络钳制(覆盖代理环境变量 + PATH 前置 stub),**审批/提权放在 agent 层**(工具调用前的 approval flow),不是 OS 级 broker。
  - 已知限制(转述):任何 Everyone SID 已有写权限的目录防不住。
- 结论:封闭在 Codex 内,不可独立复用;其"AppContainer 粒度对 agent 工作流太粗"的取舍值得记录。

### 1.3 Apache Maka

- 公开设计文章:AppContainer + 原子 Job + **one-shot Broker**,fail-closed 安全基线;引用 Codex/Gemini CLI/Claude Code/OpenCode 的 Windows 隔离边界作为证据来源。
- 定位为方案叙述,无独立可复用工具发布。

### 1.4 其他

- **Nono**:WSL2 + Landlock,非原生 Windows 机制。
- **Chromium sandbox/win**:restricted token + Job + 完整性级别 + 备用桌面,库级质量但深度耦合 Chromium 构建体系,不能独立给 agent 用。
- **Windows Sandbox / WDAG**:Hyper-V VM,秒级启动 + 体积重,agent 逐命令场景不适用。
- **Sandboxie**:内核驱动,安装面大。

## 2. 与目标需求的差距矩阵

需求:① 文件默认拒绝 + 白名单 + **用户授权提权**;② CPU/内存/磁盘预算;③ 默认仅回环 + **外网按需授权**。

| 需求 | landstrip | Codex | Maka |
|---|---|---|---|
| 文件默认拒绝+白名单 | ✅ | ✅ | ✅ |
| 资源预算(Job) | ⚠️ 仅 KILL_ON_JOB_CLOSE | ⚠️ | ⚠️ |
| 仅回环 | ⚠️ 全开/全关两档 | ⚠️ 钳制手段非内核级 | ✅ |
| **用户授权提权(broker 闭环)** | ❌ 明确拒绝 | ❌ 审批在 agent 层 | ⚠️ broker 存在但非用户授权闭环 |
| 每任务一次建沙箱、多次执行复用 | ⚠️ per-run | - | - |

## 3. 结论

- 机制验证充分:AppContainer(含 LowBox token 免 profile 路线)+ Job + ACL 白名单是三家收敛的做法;
- **"越界 → 具体路径/IP → 用户授权 → 精确放行"的 OS 级 broker 闭环是公认空白**——landstrip 拒绝做、Codex 推给 agent 层;
- 因此自研工具的差异化定位 = 在 landstrip 式的基线(默认拒绝/Job/回环)之上补齐授权 broker 与资源预算四件套。
