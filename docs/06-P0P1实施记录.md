# 06 · P0 / P1 实施记录：不解析、不猜测、程序零配合地拿到精确越界目标

> 实施日期：2026-11-07 · 前置调研见 `docs/05` · 方案基线见 `docs/04`
> 目标：把「运行时才发起的、无法静态解析的越界」也变成结构化信息交给 agent，
> 且不解析命令行、不猜测 stderr、不要求被跑的程序改造。
> 顺序：**P0 强制代理（网络）→ P1 内核违规日志（文件）**，P2/P3 暂不实施。

---

## 0. 结论速览

| 能力 | 状态 | 真机验证 |
|---|---|---|
| P0 网络：精确 `host:port` 自动采集 | ✅ 三平台（Windows/Linux/macOS） | macOS 真机 T6a–T6d 全过；Linux/Windows 由 CI |
| P0 网络：用户授权后**运行中放行、命令不重跑** | ✅ 三平台 | macOS 真机 `proxy_status=200` + `spawned` 计数=1 |

| P1 文件：授权 → 重执行 → 落盘 | ✅ macOS（沿用 B 契约 launcher retry） | T7c/T7d/T7e |
| 程序零配合 | ✅ `burn write` / `burn proxy` 均不调用 `escalate` | 断言覆盖 |

**对上一轮判断的更正**：之前判断「底层不会上报具体信息」是错的。准确说法是
「当前项目选用的三种隔离机制本身不带回调，但操作系统另有通道」：

- macOS 内核自己会写 `com.apple.sandbox.reporting:violation`，含**完整精确路径**；
- 网络目标可以不做「拦截后反查」，而是让所有出口**必经代理**，目标由 CONNECT 协议自带；
- Linux 的 `fanotify FAN_OPEN_PERM`、Windows 的 minifilter / WFP 还能做到**同步裁决**（P2/P3）。

## 1. 统一外层事件契约

三类来源（程序主动上报 / 代理 / 内核日志）归一成同一条 `violation`：

```json
{"event":"violation","kind":"net","host":"example.com","ip":"","port":443,
 "reason":"needs-approval","source":"proxy","command_id":"...","attempt":1}

{"event":"violation","kind":"file","path":"/private/tmp/.../t7.txt","access":"write",
 "reason":"needs-approval","source":"sandbox-log","command_id":"...","attempt":1}
```

`source` 取值：`explicit`（程序主动 `escalate`）/ `proxy` / `sandbox-log`。
配套事件：`proxy.deny`、`net.grant`、`violation.captured`、`violation.capture.miss`、`retry`。

**授权清单不写回基线策略文件**（`docs/04` §2 决策）：只存在本次任务的内存状态里，
`net.grant` 带 `scope:"task"`；文件侧沿用既有 `State.granted` + 一次性 token。

## 2. P0 · 强制代理

### 2.1 原理

沙箱内没有外网（`--unshare-net` / `(deny network*)` / 无 internet capability），
只留回环到代理。遵守 `HTTP(S)_PROXY` 的程序每次出站都会发 `CONNECT host:port`，
**目标信息是协议自带的**，不需要解析命令、不需要读 stderr、不需要程序改造。

### 2.2 三平台实现

| 平台 | 代理位置 | 沙箱内 relay | 代码 |
|---|---|---|---|
| Linux | 宿主 UDS `net.sock`（broker dir 已 ro-bind 进 bwrap） | `__relay_only` 独立进程监听回环端口，TCP↔UDS | `unix/netproxy.rs`、`unix/relay.rs` |
| macOS | 同上 | 同上；SBPL 追加 `net.sock` 的 `local unix-socket` 放行 | `macos/seatbelt.rs` |
| Windows | 宿主直接监听 `127.0.0.1:<随机端口>`（AppContainer 已有回环例外，无需 relay） | 无 | `win/netproxy.rs`、`run.rs` |

- 沙箱入口统一为 `aisbx __unix_entry <cmd-json>`：**`exec()` 目标命令，PID 不变**，
  relay 拆成独立进程（由 launcher 的进程组 `kill(-pgid, SIGKILL)` 兜底回收）。
  这个改动同时解决了 P1 的 PID 归属问题（见 §3.2）。
- **Linux 专属坑**：`bwrap --clearenv` 会清掉 launcher 注入的环境变量，
  `AISBX_RELAY_PORT` 必须由 `RunCtx.relay_port` 显式写进 `--setenv`；
  首轮 CI 在 ubuntu-latest 上 16 项失败即由此引起（macOS/Windows 无此问题）。
- 未授权目标：写 `violation` + `proxy.deny`，代理**等待用户授权最多 12s**；
  授权到达即放行本次连接，**命令不需要重跑**（这是与文件侧 B 契约的关键差异）。
- `authorize --host <host> --port <port>` 走既有宿主控制通道，且必须校验
  `no-real-violation`：不许凭空放行一个从未被真实拒绝过的目标。
- 防 SSRF：解析目标后拒绝 loopback / 私有网段 / link-local / 云元数据地址。
- 放行清单仅本次任务有效，不写回策略文件。

### 2.3 覆盖边界（如实标注 `partial`）

- 只覆盖**遵守代理环境变量**的程序（curl / git / npm / `burn proxy` 等）。
  裸 socket、忽略 `HTTP_PROXY` 的客户端（ssh、多数数据库驱动）仍由内核默认拒绝，
  **拿不到精确目标**——Claude Code 官方文档也承认同一限制。
- 原型只实现 HTTP `CONNECT` 隧道，未实现 SOCKS5、绝对 URI 的普通 HTTP GET、TLS 终止。
- 宿主侧上游不可达（CI 常无外网）时仍回 200 表示「策略已放行」，并写
  `proxy.upstream_unreachable` 审计，不假装连上了。

## 3. P1 · macOS 内核违规日志

### 3.1 原理

本机实测（2026-11-06/07，macOS 26.3）：Seatbelt 拒绝时内核写出

```text
[com.apple.sandbox.reporting:violation]
Sandbox: burn(71699) deny(1) file-write-create /private/var/.../outside/t7.txt
```

含 PID、被拒操作、**完整精确路径**，且带结构化 subsystem/category。
`/usr/bin/log show --last 1m --info --debug --predicate ...` 普通用户即可读取。

### 3.2 两个实测踩坑（都已修）

1. **PID 归属**：`sandbox-exec` 直接 exec 的进程会上报；早期入口再 `spawn` 一层目标命令时，
   日志里的 PID 是孙进程，按入口 PID 过滤会漏，且实测内核干脆不上报。
   → 改为入口 `exec()` 目标命令（PID 不变）+ relay 独立进程；入口同时通过 `esc.sock`
   登记自己的 PID，launcher 用「入口 PID + 登记 PID」集合归属。
2. **落盘延迟**：子进程刚退出时查 `log show` 会查不到（日志秒级落盘）。
   → `collect()` 重试 3 次、间隔 800ms；仍为空则产出 `violation.capture.miss`，
   **不静默当作「没有越界」**。

附带处理：
- 进程加载期会顺带产生 `/dev/dtracehelper`、`/dev/tty` 等系统设备拒绝，
  已用系统路径前缀过滤，避免变成给用户看的授权请求。
- SBPL 的 `(with report)` 修饰符**不适用于 deny 动作**（`sandbox-exec` 明确报
  "report modifier does not apply to deny action"），不能靠它增强上报。
- 策略开关 `broker.violation_capture`（默认 `false`）：新能力不改变既有行为，
  开启后采集到的 violation 会置 `needs_approval`，由既有 B 契约 launcher 等待授权并重跑。

### 3.3 覆盖边界（能力报告标 `partial`）

需策略显式开启；依赖统一日志秒级落盘与 `--last 1m` 时间窗；仅归属登记 PID；
更深层 fork 出的子进程仍可能漏；日志有 duplicate 合并。

## 6. 对 `docs/05` 竞品结论的补充（2026-11-07 重读一手资料）

| 发现 | 来源 | 对本项目的意义 |
|---|---|---|
| srt 的 violation 来源明确是 **seatbelt log lines + seccomp events + proxy denies**，用 `commandId` 归因，`SandboxViolationStore` 存储，`annotateStderrWithSandboxFailures` 附加给模型 | `anthropics/sandbox-runtime` README 一手 | 证实「内核日志 + 代理」是业界采用的路径，不是我们的臆想；我们已落地同源能力 |
| Claude Code 官方文档：网络被拒时**把 host 写进命令结果**，并「re-runs the command with the host added」；`registerCommandNetworkLists` 是**仅本次命令有效**的白名单 | Claude Code Sandboxing 文档一手 | 印证「一次性授权清单、不写回基线」；我们在网络侧更进一步（运行中放行，不重跑） |
| srt `--control-fd` 明确说明**文件系统规则运行中不可变**（已在 profile / bwrap argv / Windows ACE 中），只有网络列表能热更新 | README 一手 | 再次印证文件侧必须走重执行 / 内核回调，网络侧可热更新 |
| Codex 的 `on-failure` 审批靠**退出码**触发更宽松模式重跑，不做精确路径采集；网络只有全开/全关 | 官方片段 + 第三方逐文件分析（二手，待源码核实） | 说明「精确感知 + 补路径重跑」在主流产品里仍是空白，我们的 P1 有差异化价值 |
| Claude Code 原生 Windows **不提供沙箱**（需 WSL2）；srt Windows 是 alpha（专用账户 + WFP + 受限令牌） | 官方文档 / README 一手 | 我们保留 AppContainer 原生 Windows 后端是正确选择 |

| P3 | macOS Endpoint Security `ES_EVENT_TYPE_AUTH_OPEN` | 结构化 `es_file_t.path` + 同步裁决，替代日志这种事后通道；需 entitlement、公证、系统扩展批准 |
| P3 | 网络补齐 SOCKS5 / 透明代理 / 绝对 URI | 覆盖不遵守代理变量的客户端；或按平台用 WFP / nftables REDIRECT |
| 工程 | 能力报告逐项标注采集进度 | 已做；P2/P3 落地后再上调 `full` |
| 工程 | Windows 原生 P1（文件侧自动采集） | 当前 `unavailable`，未做 |

> 原则不变：**不假装安全**。任何降级都在 `capabilities --json` 里结构化上报，
