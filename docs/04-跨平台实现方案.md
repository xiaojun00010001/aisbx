# 04 · 跨平台实现方案（Windows / Linux / macOS）

> 状态：**设计方案 v1.2 — 方案 B 已实施**（见 §10；竞品调研见 `docs/05`）。三平台后端已落地并由 GitHub Actions 验证
> 依据：`sandboxing-principles-matrix.zh.md`（Agent 沙箱六项第一性原理）、`docs/01-调研报告.md`、`docs/02-设计与实现.md`、`docs/03-场景使用指南.md`、现有 Windows 实现与 `scripts/smoke.ps1` 的 18 项断言
> 范围约束：阶段一允许三平台**各自独立实现**（不要求交互/CLI 统一），但必须满足**同一份能力契约**（§2）；任何无法等价的能力必须显式登记为「不等价项」，禁止静默降级

---

## 0. 结论先行

1. **工程组织：同一个 workspace、同一个二进制 crate，不需要拆成多个项目。** 平台差异用 `#[cfg(target_os = ...)]` 模块分区 + `Cargo.toml` 的 `[target.'cfg(...)'.dependencies]` 分区表达；顶层 `main.rs` 只做**一次**分发，平台目录内不再散落 `cfg`。Cargo 一次构建只产出**一个目标平台**的二进制，三个平台靠 `--target` + CI 矩阵分别构建，产物名相同、按 triple 归档。
2. **技术选型的关键约束不是「能不能隔离」，而是「能不能在运行中精确放行」。** Windows 实现之所以能做 broker 授权闭环，是因为它的文件 PEP 是**对象侧可变的 ACL**（宿主可随时 `icacls /grant`），而不是进程内固化的规则集。Landlock 与 Seatbelt 的规则集在进程启动后**只能收紧、不能放宽**，直接照搬会永久失去 C06–C10 的运行时提权能力。
3. 因此三平台统一采用**分层 PEP**：
   - 文件维度 = **专用身份 + 对象侧可变 ACL**（Windows: package SID + NT ACL；Linux: 专用 UID + POSIX ACL；macOS: 专用 UID + APFS ACL），这是唯一能支持运行中精确放行的层；
   - 网络 / IPC / exec / 内核面 = 静态机制（Windows: capability + CheckNetIsolation；Linux: network/user/mount/pid namespace + seccomp + 可选 Landlock；macOS: Seatbelt profile）；
   - 资源预算 = Job Object / cgroups v2 / setrlimit（macOS 无 cgroups 等价物，见 §7）；
   - 进程树兜底 = Job `KILL_ON_JOB_CLOSE` / `cgroup.kill` + subreaper / process group + 父进程监督。
4. **必须正视的特权差异**：Windows 版「无需管理员」；Linux/macOS 的专用 UID 切换需要 `CAP_SETUID`（或已配置 `subuid` 的 user namespace）。阶段一在 CI（ubuntu-latest / macos-latest 均可 `sudo`）走完整能力路径，无特权时**显式降级**并标注能力缺失（§7）。这是当前方案最大的已知代价。
5. **共享的是「契约」不是「交互」**：三平台可以有各自的 CLI 细节、各自的 smoke 脚本、各自的通道路径格式；但策略字段语义、能力清单、审计事件名、`--json` 事件名、冒烟断言语义必须一致，否则「同样的能力」无法验收。

## 1. 输入与约束

### 1.1 原理矩阵给出的技术清单

| 平台 | 矩阵点名的 OS 级手段 |
|---|---|
| Linux | bubblewrap（user/mount/pid/net namespace）、Landlock（路径规则、execute、TCP 端口）、seccomp-bpf、cgroups v2（cpu/memory/pids/io）、Landlock 默认拒绝、`--tmpfs`、`--clearenv`、`--ro-bind`、nftables、出站代理 |
| macOS | Seatbelt（`sandbox-exec` + SBPL profile，`deny default`）、App Sandbox entitlements、XPC、`process-exec` 规则、`mach-lookup` 拒绝、TCC、钥匙串 ACL、setrlimit / launchd 限制、Network Extension / pf |
| Windows | AppContainer / LPAC、Job Objects、ACL、CheckNetIsolation 回环例外、capability SID、WFP（需管理员）、完整性级别 |

矩阵同时给出的硬约束（直接影响本方案）：

- §4a：PEP 必须在**解析后的真实路径**上检查，不能比字符串前缀——对应 CVE-2025-54794 / 53109 / 59829 的符号链接与形近目录绕过；
- §4b：**内核无法按域名过滤**，按目的地的放行必须走宿主侧代理；
- §1b：macOS **没有可与 cgroups 相比的每沙箱 CPU/内存上限**，需要硬上限只能用 VM；
- §4：决策（PDP）与执行（PEP）分离，守卫要小到可验证；Garfinkel 2003 的 TOCTOU / 名字 vs 对象陷阱；
- §1c：每次运行独立临时空间、退出即清，绝不复用标识符；
- §2：永远用白名单不用黑名单；Rice 定理 ⇒ 不能靠「预测程序需要什么」来生成规则集。

### 1.2 阶段一范围

- 做：三个平台各自能跑 `run` / `escalate` / `authorize` / `policy-check`，满足 §2 能力契约；三平台各自的冒烟脚本；三平台 CI。
- 不做（明确排除）：统一 CLI 细节、跨平台交叉运行的二进制、统一 IPC 协议格式、syscall hook/shim、按域出站的运行时放行（矩阵已说明必须代理，列 v0.2）、WFP/Network Extension、microVM、GUI/签名 entitlements。

### 1.3 什么算「同样的能力」

判定采用**可观测行为**而非实现手段：同一份策略（路径按平台写法）、同语义的测试载荷（`burn` 的 write/mem/fork/conn/flow），三平台各自的 smoke 断言全绿；审计事件名与 `--json` 事件名一致。

允许不等价：CLI 参数名与顺序、路径分隔符与环境变量语法（`%TEMP%` vs `$HOME`）、通道载体（命名管道 vs Unix domain socket）、身份标识（SID vs UID）、错误码数值、退出码具体数值（只要求 0 / 非 0 语义）、审计 JSON 中与平台强相关的附加字段。

## 3. 技术难点：静态规则集 vs 运行时精确放行

### 3.1 为什么 Windows 能做到

`run.rs` 的流水线把身份、ACL、Job、broker 拆开：

```text
package SID（身份） → icacls 给白名单目录加 ACE（对象侧 ACL）
                   → broker 收到授权请求 → 再给【目标路径】加 ACE（同一对象侧 ACL）
```

ACL 是**挂在文件对象上的、宿主进程可随时修改**的数据。沙箱进程每次 `CreateFile` 都由内核安全引用监控器重新检查（完全中介），所以「运行中加一条 ACE」下一次 syscall 就生效。这正是矩阵 §4 的 PEP 语义，也是产品差异化定位（越界 → 具体路径 → 用户授权 → 精确放行）。

### 3.2 为什么 Landlock / Seatbelt 直接照搬会失败

| 机制 | 规则集何时固化 | 运行中能否放宽 | 后果 |
|---|---|---|---|
| Landlock | `landlock_restrict_self()` 之后 | ❌ 只能叠加更严格的层 | C10（精确放行）永久失效 |
| Seatbelt | `sandbox_init()` 之后 | ❌ profile 不可变 | 同上 |
| bubblewrap | mount namespace 建立时 | ⚠️ 需持有 userns fd + `setns` + ns 内 `CAP_SYS_ADMIN` 再 mount，复杂且易错 | 不作为阶段一方案 |
| AppContainer ACL | 不固化，随时可改 | ✅ | 现状 |

因此**不能**把「Landlock = Linux 版 AppContainer」「Seatbelt = macOS 版 AppContainer」当作等价替换。

### 3.3 备选方案与取舍

| 方案 | 能否支持 C10 | 主要代价 | 结论 |
|---|---|---|---|
| **A. 专用身份 + 对象侧可变 ACL** | ✅ | Linux/macOS 切换 UID 需要特权；POSIX ACL 依赖文件系统支持 | **阶段一选定** |
| B. seccomp user notification：broker 代 `openat` 决策并回填 fd | ✅ | 内核 5.0+；每次文件访问往返宿主；TOCTOU（Garfinkel 2003）需 `openat2 RESOLVE_*` + fd 校验；实现量大 | v0.2 备选 |
| C. 宿主文件代理 + `SCM_RIGHTS` 传 fd | ✅ | 需要 shim / 动态库注入；macOS SIP 下 `DYLD_INSERT_LIBRARIES` 对受保护二进制失效 | v0.2 备选 |
| D. macOS sandbox extension（`sandbox_issue_extension` / `consume`） | ✅ | 私有 API，无稳定 ABI/文档；签名与 entitlements 不确定 | 登记为备选，阶段一不用 |
| E. 提权后重建 profile 并重启子进程 | ❌（语义被破坏） | 丢失进程状态，违反「运行中即时生效」 | 否决 |
| F. 预先把所有可能提权的路径写进 allow 规则 | ❌（等于不设防） | 违反默认拒绝与 Rice 定理 | 否决 |

### 3.4 结论：分层 PEP

```text
                ┌── 文件维度（可动态放宽）────────────────────────┐
                │ 专用身份 + 对象侧 ACL                            │
                │  Win: package SID + NT ACL (icacls)              │
                │  Linux: 专用 UID + POSIX ACL (setfacl/libacl)    │
                │  macOS: 专用 UID + APFS ACL (chmod +a/acl_set)   │
                └──────────────────────────────────────────────────┘
                ┌── 其它维度（静态加固，无需动态放宽）─────────────┐
                │  Win: capability / CheckNetIsolation / Job        │
                │  Linux: netns+mountns+pidns / seccomp / (Landlock)│
                │  macOS: Seatbelt profile (network*/mach/exec)     │
                └──────────────────────────────────────────────────┘
                ┌── 决策面（平台无关，共享实现）───────────────────┐
                │ 策略校验 / 裁决顺序 / token store / 审计 / 应答   │
                └──────────────────────────────────────────────────┘
```

Landlock 与 Seatbelt **不用于承担文件动态放行**：Landlock 作为可选的额外收紧层（仅在 `escalation=deny` 且无运行时授权需求时启用），Seatbelt 只负责网络、Mach、进程信息与 exec 等「不需要运行中放宽」的维度。

### 4.2 Linux 后端设计

**组件**

| 组件 | 手段 | 说明 |
|---|---|---|
| 身份 | 每任务一个专用 UID（或 userns 子 UID 映射） | 取代 package SID；策略 `task` 决定标识，任务结束回收 |
| 文件 PEP | POSIX ACL（`setfacl` / `libacl`） | 白名单目录加 `u:<uid>:rwx`；精确放行给目标加 ACE；目标不存在时给父目录加 `default:` 继承 ACE |
| 路径规范化 | `openat2(RESOLVE_NO_SYMLINKS/RESOLVE_BENEATH)` 思路 + broker 侧 `realpath` | 对应矩阵 §4a；禁止按字符串前缀判定授权路径 |
| 视图隔离 | bubblewrap / 等价 `unshare`：`--unshare-all --ro-bind / / --bind <ws> --tmpfs /tmp --clearenv --unshare-net` | 空 $HOME、清空环境变量、一次性 /tmp |
| 网络 | network namespace（仅 `lo`）；外网拒绝 | 按域放行须宿主代理（v0.2），与 Windows 现状一致 |
| 内核面 | seccomp-bpf 白名单（可选 Landlock 兜底） | 缩小内核暴露面；Landlock 只在无运行时提权需求时启用 |
| 资源 | cgroups v2：`memory.max` / `cpu.max` / `pids.max` / `io.max` | 无 root 时用 user systemd scope 或降级 `setrlimit` |
| broker | Unix domain socket（`AISBX_RUNTIME_DIR/aisbx-<task>.sock`） | 提权 socket 按 UID 校验 `SO_PEERCRED`；控制 socket 仅宿主用户可连（`0600`） |
| 进程树 | `cgroup.kill` + `PR_SET_CHILD_SUBREAPER` + `PR_SET_PDEATHSIG` | 等价于 `KILL_ON_JOB_CLOSE` |
| 清理 | 撤销 ACL、删 tmpfs 内容、回收 UID、删除 socket | 对应 C20 |

**启动序列**（与 `run.rs` 的 stage1–10 对齐）

```text
1 身份：分配/校验专用 UID（task → uid）
2 路径展开 + 规范化（$HOME / ${VAR} 展开，realpath 解析）
3 白名单 ACL：write 目录 rwx / read 目录 r-x / 策略文件 r--
4 网络：建 netns，lo up，默认无路由；internet=true 时挂 veth/代理
5 视图：unshare user/mount/pid + 只读根 + 绑定工作区 + tmpfs /tmp + --clearenv
6 预算：建 cgroup v2，写 memory.max / cpu.max / pids.max
7 broker：启动 UDS 服务（提权 + 控制两个 socket，先于进程）
8 子进程：clone/setuid 到专用 UID → 进 cgroup → exec（挂起态等价：先不 exec，全部就位再放行）
9 等待：waitpid 主进程 → 等 cgroup 内进程收敛 → cgroup.kill 兜底
10 清理：撤 ACL、删 socket、删 tmp、回收 UID、输出 exit 事件
```

**特权与降级**：`setuid` 到另一 UID 需要 `CAP_SETUID`；无特权环境优先尝试 userns + `subuid` 映射，仍不可用时降级为 **Landlock-only 模式**（文件默认拒绝/白名单有效，但 C08–C10 运行时提权不可用），必须在启动日志与能力报告中显式标记，禁止静默。

### 4.3 macOS 后端设计

| 组件 | 手段 | 说明 |
|---|---|---|
| 身份 | 每任务专用 UID（需 root 切换） | 无 user namespace 可用，这是硬约束 |
| 文件 PEP | APFS POSIX ACL：`chmod +a` / `acl_set_file` | 与 Linux 同构；目录 ACE 用继承标志 |
| 静态加固 | Seatbelt（`sandbox-exec` + SBPL profile） | `(deny default)` 起手，按需 `allow` 网络 local、`process-exec`、`mach-lookup`；**文件维度交给 ACL**，避免静态 profile 卡住动态放行 |
| 网络 | Seatbelt `deny network-outbound` + 仅允许 local | 按域放行需 Network Extension / pf / 代理（v0.2） |
| 资源 | `setrlimit`（RLIMIT_AS / CPU / NPROC / NOFILE / RSS） | **无 cgroups 等价物**：`memory_mb_total` 与 `cpu_percent` 由宿主采样 + 超限终止实现软限制 |
| broker | Unix domain socket + `LOCAL_PEERCRED` 校验 | 控制 socket 仅宿主用户可连 |
| 进程树 | `setpgid` + 父进程监督线程 `kill(-pgid)` | 无 `PR_SET_PDEATHSIG`；宿主退出由监督线程兜底 |
| 残余 | 每 run 独立临时目录，退出即删；ACL 撤销 | 矩阵 §1c 明确要求 |

**风险登记**：`sandbox-exec` 在近期 macOS 上被 Apple 标记为 deprecated（仍可用）；SBPL 无正式文档；App Sandbox entitlements 需签名，不适合 CLI 工具。阶段一以 `sandbox-exec` 为主，并把 profile 生成逻辑集中在一个模块，便于后续替换。

### 4.4 Windows 现状需要抽出的共享部分

`win/broker.rs` 中以下逻辑与 Windows 无关，应下沉到 `core`（阶段 1），供三平台复用：

- `TokenStore` / `IssuedToken` / `random_token` / TTL 与一次性消费（`redeem_token` 的校验部分）
- 裁决链：黑名单前置 → token 快速路径 → 三模式 → 应答契约（`granted` / `reason`）
- `Audit` JSONL 写入（现已在 `win/audit.rs`，实际平台无关）
- `is_prefix_hit` 的**语义**（但路径规范化必须换成各平台实现）
- `prompt_user` 的非 TTY fail-closed 判定（应改用真正的 `isatty` / 控制台句柄检测）

保留在 `win/` 的：命名管道、SDDL/ACL、SID、Job、token 生成、`CheckNetIsolation`、进程创建。

## 5. Rust 工程管理方案（回答「同一个项目还是多个项目」）

### 5.1 直接回答

**同一个项目。** 具体是：一个 Cargo workspace（现有 `aisbx-policy` + `aisbx`）、一个二进制 crate `aisbx`，三套平台后端源码放在同一 crate 的不同模块里，用 `cfg` 选择；平台专属依赖写在 `Cargo.toml` 的 target 段落里。

- `cargo build` 在 Windows 上只编译 `win/`，不会编译 `linux/` / `macos/`，也不会链接 `libc`/`nix`；
- 在 Linux 上只编译 `linux/`，不会链接 `windows-sys`；
- 一次构建产出**一个**目标平台的 `aisbx`（或 `aisbx.exe`）；三个平台的产物靠三次构建（通常在三台 CI 机器上）得到，这是 Cargo 的正常模型，**不是缺陷，也不需要拆项目**。

### 5.2 三种组织方式对比

| 方式 | 结构 | 优点 | 缺点 | 何时选 |
|---|---|---|---|---|
| **A. 单 crate + cfg 模块（推荐）** | `aisbx-policy` + `aisbx`（内含 `win/ linux/ macos/ core/`） | 策略契约天然共享；单版本号、单 CLI、单发布物；CI 简单；增量编译快 | 单 crate 内平台代码混居，需要纪律约束 `cfg` 位置；平台依赖特性需小心 | **阶段一** |
| B. 单 workspace 多 crate | `aisbx-core` + `aisbx-win` + `aisbx-linux` + `aisbx-macos` + `aisbx-cli` | 平台边界强隔离；可独立测试/发布；trait 抽象更自然 | 多一层间接；版本/特性协调成本；阶段一代码量小，收益不抵成本 | 平台实现各自 >3k 行、需要独立 crates.io 发布、或出现互斥依赖时 |
| C. 三个独立仓库 | 三份代码 | 完全解耦 | 策略契约与能力清单会分叉；重复修 bug；无法保证「同样能力」 | **否决**：与本任务目标直接冲突 |

迁移路径：A → B 是纯重构（把目录提升为 crate，公共部分下沉 `aisbx-core`），不需要改 CLI 与策略格式，随时可做。

### 5.3 推荐目录结构

### 5.4 Cargo.toml 的 target 分区

```toml
# 根 Cargo.toml
[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
windows-sys = { version = "0.52", features = [ /* Win32_* */ ] }
nix = { version = "0.29", features = ["user", "mount", "sched", "process", "signal", "socket", "uio", "fs", "resource"] }
libc = "0.2"

# crates/aisbx/Cargo.toml
[dependencies]
aisbx-policy = { path = "../aisbx-policy" }
serde = { workspace = true }
serde_json = { workspace = true }

[target.'cfg(windows)'.dependencies]
windows-sys = { workspace = true }          # ← 从通用依赖移到此处

[target.'cfg(target_os = "linux")'.dependencies]
nix = { workspace = true }
libc = { workspace = true }

[target.'cfg(target_os = "macos")'.dependencies]
nix = { workspace = true }
libc = { workspace = true }
```

要点：把 `windows-sys` 从 `[dependencies]` 移到 target 段是阶段 0 的第一步（否则 Linux/macOS 也会解析并编译这份依赖树）；`aisbx-policy` 保持在通用段，它就是三平台共享的契约。

**v1.1 补充（multicall helper）**：Landlock/seccomp 必须在 bubblewrap 建立视图**之后、目标进程 exec 之前**于进程内应用。Codex 用独立 helper 二进制、srt 用 `apply-seccomp` 多调用二进制；本项目采用**单二进制 multicall**：同一 `aisbx`，当 `AISBX_ROLE=helper` 时走 helper 入口（应用 Landlock/seccomp 后 exec 目标命令），避免多产物打包，同时保留单 crate 单版本。

### 5.5 cfg 分层原则

1. **依赖层**：`Cargo.toml` 的 `[target.'cfg(...)']`，决定「编译哪些外部 crate」；
2. **模块层**：只在 `main.rs` / `backend/mod.rs` 出现 `#[cfg(target_os)]`，决定「编译哪些源码目录」；
3. **平台目录内部不再写平台 cfg**，避免 `#ifdef` 蔓延；
4. **必须提供 `unsupported` 后端**：非三平台 target 也能 `cargo check` / `cargo test` 通过，返回清晰错误，而不是编译失败；
5. `examples/burn.rs` 里的平台差异（路径、内存、fork、socket）允许少量局部 cfg，但断言语义保持一致；
6. 单元测试里需要 root / 内核特性支持的用例统一 `#[ignore]` 并注明前置条件，CI 用专门 job 跑。

### 5.6 共享 core 与平台边界

阶段一按用户约束「不要求交互统一」，因此**不强制**引入统一 trait；但建议保留一个极薄的后端边界，便于阶段 4 验收：

```rust
// backend/mod.rs
pub struct RunRequest<'a> { pub policy: &'a Policy, pub policy_file: &'a str, pub cmd: &'a [String], pub json: bool }
pub fn run(req: RunRequest<'_>) -> Result<i32, String>;
pub fn escalate(policy: &Policy, path: &str, access: &str, token: &str) -> Result<i32, String>;
pub fn authorize(policy: &Policy, path: &str, access: &str, ttl: u64) -> Result<i32, String>;
```

三个平台各自实现这三个自由函数，`core` 只提供协议/裁决/token/audit。**不统一 CLI 形态**：Linux/macOS 可以各自决定 `--` 之后的命令解析、路径环境变量语法等，只要 `--json` 事件名与审计事件名一致。

### 5.7 构建、target triple 与交叉编译的现实

| 平台 | 常用 triple | 备注 |
|---|---|---|
| Windows | `x86_64-pc-windows-msvc` / `aarch64-pc-windows-msvc` | MSVC 链接器，或 `x86_64-pc-windows-gnu`（现有交叉 check 用） |
| Linux | `x86_64-unknown-linux-gnu` / `aarch64-unknown-linux-gnu` / `x86_64-unknown-linux-musl` | musl 便于静态分发；cgroups/ACL 依赖运行内核 |
| macOS | `x86_64-apple-darwin` / `aarch64-apple-darwin` | 需要 macOS SDK / Xcode CLT；不能从 Linux 合法交叉构建 |

- `cargo check --target <triple>` 只做**类型检查**，不验证内核行为；Landlock/Seatbelt/cgroups/ACL 必须在**真实内核**上跑冒烟；
- 跨平台交叉编译需要对应链接器与 sysroot，且 `build.rs` / proc-macro / C 依赖容易踩坑；阶段一**不做跨平台交叉发布**，采用「各平台原生构建」；
- 三个平台的 `Cargo.lock` 是同一份（Cargo 会记录所有 target 的依赖），这点无需拆分。

### 5.8 CI 与冒烟

```yaml
strategy:
  matrix:
    include:
      - { os: windows-latest, script: ./scripts/smoke.ps1 }
      - { os: ubuntu-latest,  script: ./scripts/smoke-linux.sh }
      - { os: macos-latest,   script: ./scripts/smoke-macos.sh }
steps:
  - uses: actions/checkout@v5
  - run: cargo test -p aisbx-policy            # 契约单测，三平台都要过
  - run: cargo build --release --bins
  - run: ${{ matrix.script }}                  # 同语义的能力断言
  - uses: actions/upload-artifact@v6          # 按 runner.os 命名，避免覆盖
```

三份 smoke 共享 `scripts/capability-matrix.md` 里的断言编号与语义；Windows 的 18 项断言是基线，Linux/macOS 至少覆盖 C01–C15、C17–C21，无法覆盖的必须写明原因。

### 5.9 版本与发布

- 单 crate 单版本号，二进制统一命名 `aisbx`（Windows 为 `aisbx.exe`）；
- artifact 按 `aisbx-<version>-<target-triple>` 归档，不要用同一个 artifact 名（会互相覆盖）；
- 需要一键出多平台包时再引入 `cargo-dist` / `cross`，阶段一不需要。

### 5.10 常见坑（实施检查单）

- `cfg(target_os = "macos")` 拼错 / 误用 `cfg(target_family = "unix")` 导致 Windows 代码混入；
- `Cargo.toml` 的 `[target.'cfg(unix)'.dependencies]` 与 `build.rs` 里的 `CARGO_CFG_TARGET_OS` 不是同一套机制；
- `#[cfg]` 模块被排除后，其 `use` 残留造成非目标平台编译失败 → 用 `unsupported` stub 兜住；
- `cargo test --all-targets` 会把 `examples/burn.rs` 也编进去，平台差异要一并处理；
- IDE / rust-analyzer 默认只按宿主 target 分析，Windows 改动在 mac 上不会即时报错 → 依赖 CI 与 `cargo check --target`；
- `windows-sys` 特性开关很多，缺一个特性在 Windows CI 才暴露；
- `nix` 的 feature 组合随版本变化，锁版本；
- macOS `sandbox-exec` 的 SBPL 语法无官方文档，profile 生成器要有单测与真机验证；
- 不要把「检测不到 TTY」当成 Windows 专有逻辑：三平台 `prompt` 都应 fail-closed。

## 6. 分阶段实施计划

| 阶段 | 内容 | 验收标准 | 主要风险 |
|---|---|---|---|
| **0** 工程骨架 | ① `windows-sys` 移入 `[target.'cfg(windows)'.dependencies]`；② 新增 `backend/` 与 `unsupported` stub；③ 三平台 `cargo check --all-targets` + `cargo test -p aisbx-policy`；④ 新增 `cross-platform.yml` 的 check-only 矩阵 | Windows 冒烟 18 项保持全绿；mac 本机 check 通过；Windows 交叉 check 通过 | 依赖移动导致 Windows CI 编译失败 → 先本地交叉 check 再推送 |
| **1** 共享 core 下沉 | 把 `decision / tokens / audit / protocol` 从 `win/broker.rs` 提到 `core/`，Windows 后端改为调用；补单测（重放、TTL、黑名单、非 TTY） | Windows 冒烟全绿；core 单测通过；无行为变化 | 重构破坏现有管道协议 → 用现有 smoke 做回归闸门 |
| **2a** Linux portable（新增） | bwrap + Landlock + 反逃逸 seccomp + netns + multicall helper；`smoke-linux.sh` | C01–C07、C17–C21 全绿；C08–C10 在能力报告标 `partial` | bwrap/seccomp 依赖、发行版差异 |
| **2b** Linux strict | UID + POSIX ACL + cgroups v2 + UDS broker（`SO_PEERCRED`）+ 进程树兜底 + 清理 | C01–C15、C17–C21、C23 全绿；C08–C10 转 `full` | ACL 文件系统支持、userns 可用性、cgroup 委托权限 |
| **3a** macOS portable（新增） | SBPL 模板 + 参数化生成器 + 单测 + 违规日志 + `sandbox-exec -p` 探测 | 同 2a；C13/C14 标「软限制」 | sandbox-exec 可用性、SBPL 无文档 |
| **3b** macOS strict | UID + APFS ACL + setrlimit + UDS broker + process group 兜底 | 同 2b；C13/C14 仍为软限制 | 需 root、无 cgroups |
| **4** 三平台验收 | CI 矩阵全开、`capabilities --json` 断言、能力矩阵报告、文档更新、不等价项白名单、Windows 侧清理补强 | 三平台 CI 全绿；`scripts/capability-matrix.md` 与实际一致 | 三平台行为漂移 → 以共享能力清单为唯一真值 |

**依赖顺序**：0 与 1 是所有平台的前置；2a/3a（无特权、风险低）先打通三平台 CI 与能力矩阵，再做 2b/3b 补齐 C08–C10；4 收口。阶段 0/1 严格不改变 Windows 可观测行为。

> **v1.1 阶段 1 增量**：`core` 下沉时同时增加 `command_id` 审计字段、`CapabilityReport` 数据结构与依赖探测接口。
>
> **v1.1 双模式决策**：`strict` 为默认与验收基线（用户要求「同样的能力」，C10 不可降级）；`portable` 作为无特权环境路径，其「授权后以更宽松策略重跑命令」必须显式登记为 partial，不得计入「全部通过」。详见 `docs/05` §5。

## 7. 风险登记与降级行为（对应矩阵六原则）

| # | 风险 | 影响能力 | 缓解 / 降级 | 原理 |
|---|---|---|---|---|
| R1 | Linux/macOS 切换专用 UID 需要 `CAP_SETUID`；与 Windows「无需管理员」不对等 | C02 C03 C10 | CI 走 sudo；本地优先 userns+subuid；否则显式降级为 Landlock-only / Seatbelt-only，并在启动日志与能力报告标注「运行时提权不可用」 | 最小权限 |
| R2 | POSIX/APFS ACL 依赖文件系统支持（网络盘 / FAT / FUSE 可能不支持） | C02 C03 C10 | 启动前探测；不支持则 fail-closed 报错，不静默放行 | 默认拒绝 |
| R3 | 授权路径未规范化（符号链接 / `..`）导致越权放行 | C06 C10 | broker 侧 `realpath` + 目标存在性校验；Linux 用 `openat2 RESOLVE_*`；Windows v0.2 补 `GetFinalPathNameByHandle` | PEP / 完全中介 |
| R4 | macOS 无 cgroups 等价物 | C13 C14 | `setrlimit` 硬限单进程；全任务内存/CPU 由宿主采样 + 超限 kill（软保证），写入能力矩阵 | 资源预算 |
| R5 | `sandbox-exec` 被弃用、SBPL 无文档 | C17 C18 | profile 生成集中在一个模块并加真机测试；后续可切 App Sandbox entitlements（需签名） | 组合 |
| R6 | 内核无法按域名放行 | C18 精确放行 | 三平台统一：宿主侧回环代理（矩阵 §4b / docs/03 §2.4），v0.2 | 受控信息流 |
| R7 | 环境变量 / 点文件泄漏凭据 | 默认拒绝 | Linux `--clearenv` + 空 $HOME；macOS 清 env + Seatbelt 拒绝 `~/.ssh` `~/.aws`；Windows 保持 AppContainer | 密钥 |
| R8 | 共享内核（三平台共同） | 隔离 | 明确登记：不是 VM 级隔离；敌对租户场景建议 microVM | 隔离 |
| R9 | 宿主崩溃残留孤儿进程 / ACL 未撤销 | C19 C20 | cgroup.kill / process group 监督 + 启动时清理同 task 的陈旧资源；**Windows 当前提权 ACE 未纳入 cleanup，需一并修** | 残余与复用 |
| R10 | broker 通道被冒名或串任务 | C21 | UDS 0600 + peer credential 校验；Windows 保持双 ACE DACL + Low 标签 | 组合 / PEP |
| R11 | 三平台实现漂移，「同样能力」名不副实 | 全部 | 共享能力清单 + 三份 smoke 断言编号对齐 + CI 矩阵；任何降级必须写进白名单 | 组合 |
| R12 | bwrap 只读 bind 被沙箱内自建 userns + mount/umount 拆除 | C02 C03 | seccomp 反逃逸过滤器禁 `unshare`/`clone(NEWUSER,NEWNS)`/`setns`/`mount`/`umount2`/`pivot_root`/`clone3`，并设 `user.max_user_namespaces=0`；CI 加「尝试 unshare/mount 必失败」断言 | 默认拒绝 |
| R13 | 内核/发行版差异导致「看似启动、实则未生效」 | 全部 | Landlock `NotEnforced` 检查、ABI 探测、`--probe`、依赖版本探测、`--require-full`、结构化 `SANDBOX_UNAVAILABLE` 失败 | fail-closed |
| R14 | macOS 为兼容工具放行 trustd/pty/AppleEvents，削弱隔离 | C17 C18 | 例外逐项默认关闭并登记，能力报告标 partial | 最小权限 |
| R15 | 代理方案被 DNS rebinding / 云元数据 / 私网绕过 | C18 | 未来代理必须实现 resolved-address check（拒 loopback/link-local/元数据/私网/IPv4-mapped），按矩阵 §4b 事故清单写用例 | 受控信息流 |

## 9. 竞品调研后的方案修订（v1.1）

依据 `docs/05` 对 Claude Code（sandbox-runtime）、OpenAI Codex、dsh（DeepSeek Harness）的调研，修订如下，**阶段 1 起生效**：

1. **差异化确认**：三家均无「运行中按具体路径修改 OS 文件 PEP」能力（srt 运行中仅能改网络规则；Codex/dsh 的审批是换策略重跑）。C06–C10 的 broker 闭环保留，§3 的核心判断成立。
2. **新增 strict / portable 双模式**：portable 用 bwrap/Landlock、Seatbelt 静态规则（无需特权），C08–C10 标 partial；strict 仍为验收基线。实施顺序 2a/3a → 2b/3b。
3. **M1 反逃逸**：Linux seccomp 必须禁 userns/mount/setns/umount2/pivot_root/clone3，否则 bwrap 隔离可自拆。
4. **M2/M3/M8 能力探测**：Landlock `NotEnforced` 检查、`--probe`、依赖清单、新增 C23 `capabilities --json` 与 `--require-full`，取代「仅日志标注」的降级方式。
5. **M5 单二进制 multicall**：Linux helper 通过 `AISBX_ROLE=helper` 复用同一二进制（见 §5.4 补充）。
6. **M6 macOS 工程化**：SBPL 静态模板 + 参数化生成器 + 单测 + 违规日志；平台例外默认关闭并登记。
7. **M7 审计归因**：审计事件增加 `command_id`（≥128bit）。
8. **M9 路径规范化口径**：策略/token 前缀比较统一 canonicalize，审计同时记录原始与规范化路径；OS 层 PEP 仍检查真实对象（兼顾 Claude Code「不做 symlink resolve」的经验与矩阵 §4a）。
9. **M10 网络代理预留**：仅回环 + 宿主 HTTP/SOCKS5 代理 + 域名白名单接口；未来代理必须带 resolved-address check。阶段一能力不变。
10. **M11 Windows 补强**：提权 ACE 纳入会话级 refcount + 崩溃恢复清理（修 R9）；评估 `FILE_DELETE_CHILD` deny 与 Low no-write-up 标签；补测 AppContainer 下 HTTPS/证书存储可用性。
11. **风险登记**：新增 R12–R16（见 §7）。
12. **可直接参考的实现清单**：见 `docs/05` §4.3。

本轮仅修订方案，**未写任何平台实现代码**。

## 10. 方案 B 实施记录（v1.2）

用户最终选定的统一契约：**策略配置 → 拒绝感知 → 用户授权 → 重新执行命令**。
`strict/portable` 双模式、专用 UID + 对象侧可变 ACL（`2b/3b`）**全部取消**；Windows 现有的
进程内即时放行保留为实现细节，但不再作为对外契约。

### 10.1 统一契约

```text
策略 Policy → run(策略快照) → 沙箱内执行
  → 内核拒绝 + 程序显式上报 → violation{command_id, attempt, path|host, reason}
  → agent 展示目标 → 用户同意 → authorize 签发一次性 token(仅基于真实拒绝)
  → launcher 以「放宽后的策略快照」重新 spawn(attempt+1) → 成功
```

约束：`command_id` 由宿主生成不可伪造；授权目标必须严格宽于旧策略且不超批准范围；
同一 `command_id` 的资源预算不随 attempt 重置；只有 `needs-approval` 型拒绝才等待授权。

### 10.2 实际目录结构（单 workspace、单二进制 crate）

```text
crates/aisbx/src/
├── main.rs              # CLI；一次 cfg 分发 + capabilities + __linux_helper multicall
├── backend/             # 平台名称/可用性
├── capabilities.rs      # capabilities --json + --require-full
├── common.rs            # 策略加载、路径展开
├── core/                # 平台无关:protocol / tokens / audit / decision / state
├── unix/                # UDS broker(esc.sock + ctl.sock) + launcher 重试循环
├── linux/               # bwrap 参数生成 + multicall helper(lo up)
├── macos/               # Seatbelt SBPL 模板生成器
├── win/ + run.rs        # Windows v0.1 后端(保持不动,18 项冒烟回归闸门)
examples/burn.rs         # 载荷:write/mem/fork/conn/loopback/flow/retryflow
scripts/smoke-unix.sh    # Linux/macOS 的 B 契约冒烟(能力报告驱动降级)
scripts/smoke.ps1        # Windows 原有 18 项冒烟
.github/workflows/
├── windows-smoke.yml    # Windows 18 项
└── cross-platform.yml   # ubuntu/macos B 契约冒烟 + windows 编译检查
```

### 10.3 三平台实现映射（实际）

| 维度 | Windows | Linux | macOS |
|---|---|---|---|
| 文件 PEP | AppContainer ACL | bwrap `--ro-bind / /` + 白名单/授权 `--bind` | Seatbelt `(deny default)` + 白名单/授权 `file-write*` |
| 网络 | capability + 回环例外 | `--unshare-net`（外网全断）+ helper 置 lo up | 仅 `remote ip "localhost:*"` + bind/inbound 例外；外网 `EPERM` |
| 反逃逸 | Job + 低完整性 | `--unshare-user` + `--disable-userns` | macOS 无 userns 面 |
| broker 通道 | 命名管道（双 ACE DACL） | UDS（bwrap 内 ro-bind） | UDS（`(local unix-socket (subpath ...))` 精确放行） |
| 资源 | Job（内存/CPU/进程数） | `RLIMIT_AS`（软、安全下限 512MB） | 无内核等价物，能力报告标 unavailable |
| 授权生效 | 既有 in-place（实现细节） | 重执行（新 bwrap argv） | 重执行（新 SBPL profile） |

### 10.4 关键实测结论（避免重复踩坑）

- macOS Seatbelt 的 `deny default` 连 **UDS connect** 一起挡；必须显式
  `(allow network* (local unix-socket (subpath "<esc.sock>")))`，且路径要同时登记
  `/var/...` 与 canonical 后的 `/private/var/...`。
- `(allow network* (local ip "localhost:*"))` 会匹配**所有出站连接的本地端点**，
  等于放开外网（实测 1.1.1.1 从 `EPERM` 变 `timeout`）；只允许
  `network-bind`/`network-inbound` 使用该 local 规则。
- `RLIMIT_NPROC` 按**用户**计数，不是每任务配额；设成策略值会导致沙箱内 `fork`
  全部 `EAGAIN`，因此不使用，进程数上限在能力报告中标 `unavailable`。
- macOS `RLIMIT_AS` 对 512MB 分配无效；故内存硬上限标 `unavailable`，冒烟按能力报告降级为 WARN。
- bwrap 挂载**顺序**敏感：只读 bind（策略父目录、broker 目录）必须早于可写 bind，
  否则后者被覆盖成只读。
- `--disable-userns` 依赖显式 `--unshare-user`。
- 路径规范化必须分离 `real_path`（给 OS）与 `compare_key`（仅比较），
  否则反斜杠形式会污染 bwrap bind / SBPL subpath 规则。

### 10.5 能力报告与不等价项（如实上报）

`aisbx capabilities --json` 逐项输出 `full/partial/unavailable`，`--require-full` 在
关键能力 `unavailable` 时拒绝启动。阶段一已知不等价项：

| 项 | Windows | Linux | macOS |
|---|---|---|---|
| 运行中即时放行 | ✅ 内部优化 | ❌ 重执行 | ❌ 重执行 |
| launcher 内 retry 事件 | ❌（`authorized_retry: partial`） | ✅ | ✅ |
| 内存硬上限 | ✅ Job | ⚠️ `RLIMIT_AS` 软限制 | ❌ 无等价机制 |
| 全任务内存 / CPU 硬上限 | ✅ Job | ❌ 未启用 cgroups | ❌ 无等价机制 |
| 每任务进程数 | ✅ Job | ❌ `RLIMIT_NPROC` 按用户计数不可用 | ❌ 同左 |
| 内核被动拒绝自动采集 | ❌ 显式上报 | ❌ 显式上报 | ❌ 显式上报 |
| 按域/主机运行时放行 | ❌ 需代理 | ❌ 需代理 | ❌ 需代理 |
| Landlock / seccomp / cgroups 原生 | 不适用 | ⚠️ 由 bwrap 提供部分等价 | 不适用 |

> 上述均为**显式登记**，不是静默降级；`smoke-unix.sh` 按能力报告决定断言或 WARN。
