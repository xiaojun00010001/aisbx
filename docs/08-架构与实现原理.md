# 架构与实现原理：按沙箱提供的能力与场景

> 本文按「**沙箱对外提供什么能力（capabilities）**」与「**支撑这些能力的是哪些系统、各自怎么工作**」两条线组织，
> 面向要接入/审计/扩展 aisbx 的人。每个机制都标注实现位置（`文件:行号`）。
>
> 契约基线在 `scripts/contract-baseline.json`（**改它等于改契约**，三个平台的 CI 会同时验证）；
> 能力报告的实现见 `crates/aisbx/src/capabilities.rs:79`(win) / `:119`(macos) / `:166`(linux)。

---

## 0. 一句话定位

aisbx 是一个 **「拒绝感知 → 授权 → 重跑」** 的沙箱启动器（契约 B）：它把一份策略声明翻译成
**操作系统原生的隔离机制**，在程序越界时**精确采到被拒的路径**，经宿主授权后**把该路径并入下一轮的隔离策略并重跑**。

三平台的差异只发生在「**策略 → OS 机制**」这一层；上层的策略解析、授权裁决、token 生命周期、
审计与事件流是平台无关的，**对外契约（事件名、status 字段、pending 结构）三平台完全一致**。

## 1. 架构分层

```
┌──────────────────────────────────────────────────────────────┐
│ 平台无关上层（crates/aisbx/src/core、common、aisbx-policy）      │
│  策略模型 Policy / 授权裁决 / token 生命周期 / 审计 / 事件流 / 契约 │
└───────────────┬──────────────────────────────────────────────┘
                │ 「已授权路径集合」→ OS 原生机制
┌───────────────▼──────────────────────────────────────────────┐
│ 平台后端                                                        │
│  macos/seatbelt.rs  linux/bwrap.rs  win/{token,acl,job,proc}.rs │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 位置 | 职责 |
|---|---|---|
| 契约模型 | `crates/aisbx-policy/src/lib.rs:23` | `Policy` 唯一契约；`deny_unknown_fields`（`:198`）保证拼错键必须失败 |
| 核心（Unix） | `core/{protocol,tokens,audit,decision,state}.rs` | broker 单行 JSON 协议、一次性 token、审计 JSONL、路径判定、事件模型 |
| 公共 | `common/{mod,stderr_scan,pending}.rs` | 策略加载、`%VAR%` 展开、**L1 stderr 越界路径提取**、待授权结构 |
| 分发 | `backend/mod.rs:8`、`main.rs:144-161` | 唯一一处平台判断（`cfg`） |
| Unix 共用 | `unix/{broker,run,relay,netproxy,proctree}.rs` | UDS broker、B 契约重试循环、沙箱内 HTTP CONNECT/SOCKS5 relay、宿主代理裁决 |
| Windows | `win/{token,acl,job,proc,broker,netproxy,loopback,audit}.rs` | AppContainer/Job/ACL/命名管道，**独立实现**但对外契约一致 |

**分发方式不是 trait 对象，而是「闭包注入」**：Unix 两平台共用同一个 launcher
`unix/run.rs:36 run_loop`，只把 `make_argv` 换成 `seatbelt::argv`（`macos/seatbelt.rs:85`）
或 `bwrap::argv`（`linux/bwrap.rs:21`）。

> Windows 侧 `core/*` 被镜像重写了一份（`win/broker.rs` 自带 `IssuedToken`/`decide_file`/`redeem_token`，
> `win/audit.rs` 复制 `core/audit.rs`）——因为它走命名管道 + Win32 句柄，
> 且需要 `SeSecurityPrivilege`；但**对外契约保持一致**（对照 `unix/broker.rs:329` 与 `win/broker.rs:622` 的 status 输出）。

## 2. 能力矩阵：21 个能力 × 三平台

> 「机制」列是**该能力值背后的真实 OS 机制**；`unavailable` 一律显式声明，不假装安全。
> 判定逻辑见 `crates/aisbx/src/capabilities.rs`。

| 能力键 | macOS | Linux | Windows | 机制 |
|---|---|---|---|---|
| `strategy` | full | full | full | 策略声明式（`Policy`） |
| `denial_detection` | partial | partial | partial | 三平台都只靠 L1（子进程 stderr 自报）→ 路径可被程序伪造，故 partial |
| `authorized_retry` | full | full | full | 授权并入下一轮策略快照并重跑（`unix/run.rs:186-219`、`win/run.rs` 重试轮） |
| `launcher_retry` | full | full | full | 启动器负责重试，无需被测程序配合 |
| `file_isolation` | full | full | full | Seatbelt 规则 / bwrap `--bind` / AppContainer+ACL |
| `network_egress` | full | full | full | Seatbelt 禁网 / bwrap `--unshare-net` / AppContainer 无 network capability |
| `memory_per_process` | **unavailable** | partial | full | macOS 无内核等价机制；Linux `RLIMIT_AS`；Windows Job `JOB_OBJECT_LIMIT_PROCESS_MEMORY` |
| `memory_total` | **unavailable** | **unavailable** | full | 仅 Windows Job 总量限制 |
| `cpu` | **unavailable** | **unavailable** | full | 仅 Windows Job CPU 限制 |
| `process_limit` | **unavailable** | **unavailable** | full | Windows Job `active_processes`；Linux `RLIMIT_NPROC` 按用户计数故不可用 |
| `process_tree_kill` | partial | partial | full | Unix 靠进程组（`setpgid` + `kill(-pgid)`，`unix/run.rs:154`）；Windows 靠 Job 树 |
| `auto_violation_capture` | partial | partial | partial | macOS 另有 L2 内核日志 → 仍标 partial（需策略显式开启、依赖日志落盘延迟） |
| `net_violation_capture` | partial | partial | partial | 代理通道裁决（`unix/netproxy.rs`、`win/netproxy.rs`） |
| `net_proxy` | `http-connect+socks5` | 同 | 同 | 宿主代理；**由协议自己读出精确 host:port**，不解析命令 |
| `violation_file_path_precision` | **exact** | reported | reported | macOS L2 内核日志给真实路径；Linux/Windows 只能 L1 自报 → reported |
| `violation_net_path_precision` | exact | exact | exact | 代理协议层直接给出 |
| `violation_log_probe` | `sandbox-reporting-violation` | **空串** | **空串** | 只有 macOS 有内核日志通道；空串 = 无通道（消费方只需判断非空） |
| `seatbelt` | full | unavailable | unavailable | 机制探测 |
| `bubblewrap` | unavailable | full | unavailable | 机制探测 |
| `landlock` | unavailable | partial | unavailable | Linux 上探测到但仅部分生效 |
| `seccomp` | unavailable | partial | unavailable | 随 bwrap 生效 |

**关键设计**：状态类能力值只能是 `full|partial|unavailable`（`capabilities.rs:301`），
出现别的值即契约破坏；`--require-full`（`capabilities.rs:233`）可让任何 `unavailable` **拒绝启动**，
而不是降级为「无约束执行」。

## 3. 场景机制：沙箱对外提供的每个能力怎么工作

### 3.1 文件隔离

**统一语义**：策略里的 `filesystem.write` 是**可写白名单**，`filesystem.read` 只读，
`filesystem.deny_escalation` 是**不可授权黑名单**，`allow_escalation` 只在 `auto` 模式生效。

| 平台 | 机制 | 要点 |
|---|---|---|
| macOS | Seatbelt SBPL profile（`macos/seatbelt.rs:17 profile()` → `sandbox-exec -p`） | 写**规则**不要求路径存在 → 授权「正要创建的文件」天然可行 |
| Linux | bubblewrap（`linux/bwrap.rs:21 argv()`） | `--bind` 的**源路径必须存在**，且只 bind **目录** → 授权尚不存在的文件需特殊处理（见 3.3） |
| Windows | AppContainer + ACL（`win/acl.rs`） | 目录用 `(OI)(CI)M` 继承，单文件用 `M`；**授权粒度**靠「只给该文件 ACE」而非整目录 |

**「授权粒度不外溢」在三平台如何保证**：
- Windows：给**单文件** ACE，目录不加 Modify（`win/acl.rs:56 grant_path_precise`）；
- Linux：给**单文件** `--bind`，不给父目录写权限；
- macOS：给单文件规则，父目录仍只读。

### 3.2 提权/授权模式

`EscalationMode { Prompt, Auto, Deny }`（`aisbx-policy/src/lib.rs:12`，默认 `prompt` `:133`）。

裁决顺序**三平台一致且不可颠倒**（Unix `unix/broker.rs:193`，Windows `win/broker.rs:482`）：

1. **黑名单前置**：`deny_escalation` 命中 → 直接拒绝 + 审计 `escalation.deny`。
   **token 也救不回**——token 分支在黑名单之后，够不到。
2. **token 快速路径**：`req.token` 非空 → 校验并兑换 → 白名单加宽 → 审计 `token.redeemed`；
   失败 → 审计 `token.reject` → 拒绝。
3. **模式裁决**：`auto` 需命中 `allow_escalation` 前缀；`prompt` 需 `has_tty()`（`core/decision.rs:56`）。
4. **兜底 needs-approval**：置 `needs_approval=true` + 审计 `escalation.deny{retry_required:true}`，
   由宿主 agent 走人工授权通道；无人授权则超时退出。

**非 TTY 一律 fail-closed**：`prompt` 模式在无 TTY 下不会自动放行。
Windows 侧还额外做了一次「即使进了交互提示也再判 `is_tty`」的双重检查（`win/broker.rs:803-811`）。

> 已知不对称：Unix 的 `Deny` 模式仍落到第 4 步（会空等至多 20s），
> Windows 的 `Deny` 不置 `needs_approval`（立即退出）。

### 3.3 授权「尚不存在的文件」——三平台统一为同一套语义

| 平台 | 做法 |
|---|---|
| macOS | Seatbelt 写规则，路径不存在也生效 |
| Linux | **宿主预创建空占位文件** → 对该文件做单文件 `--bind` → 任务结束**回收空占位文件**（`unix/run.rs:226`） |
| Windows | **宿主预创建空占位文件** → 对该文件授文件级 `M` → 任务结束回收（`win/acl.rs` 的 `grant_path_precise`） |

> 这正是「跨平台交互一致」的一个具体兑现点：Linux 早期只 bind 目录，
> 导致「授权后重跑」在 Linux 上**必然失败**（bwrap bind 源路径必须存在），
> 而 macOS/Windows 都正常。补齐 `T12/T13` 场景后立刻暴露，修法即上述统一语义。

### 3.4 网络

| 能力 | 机制 |
|---|---|
| 默认无外网 | Seatbelt 禁网 / `--unshare-net` / AppContainer **不注入** network capability（`run.rs:94-99`） |
| 回环放行 | macOS/Linux 直接允许 loopback；Windows 需 `CheckNetIsolation` 回环例外（`win/loopback.rs`），按 package SID 幂等「先删后加」 |
| 精确目标采集 | **宿主代理**读协议本身拿到 `host:port`（HTTP CONNECT / SOCKS5）→ 不解析命令、不改造载荷（`unix/netproxy.rs`、`win/netproxy.rs`） |
| 运行中授权 | `authorize --host/--port` 签发网络授权（`unix/broker.rs:299`、`win/broker.rs:635`），**必须基于代理真实观察过的拒绝**，否则 `authorize.reject{reason:"no-real-violation"}` |
| SSRF 防护 | 代理拒绝 loopback/私网目标（`T9d`） |

> 网络提权走**代理通道**而非 `escalation`：Unix/Windows 的 `op=="net"` 一律拒绝并审计
> `escalation.deny{reason:"network-escalation-unsupported"}`——因为网络放行是「运行中即时生效」，
> 不需要重跑。

### 3.5 越界感知：L1 与 L2

| 通道 | 来源 | 可信度 | 适用 |
|---|---|---|---|
| **L1** | 子进程 **stderr 文本**（`common/stderr_scan.rs`） | 路径由**程序自称** → 可伪造 → `precision=reported` | 三平台都有；Windows 认 `.NET` 形态（`Write-Error: Access to the path '…' is denied.`） |
| **L2** | **内核日志**（macOS `sandbox-reporting-violation`） | 内核不受欺骗 → `precision=exact` | 仅 macOS |

**对抗用例（`T15`）**验证的是二者的可信度差：程序「自称」路径 A、真实访问路径 B 时，
- L2（若有）采到的是**真实**路径 B；
- L1 采到的只能是**自称**路径 A；
- 且**授权 A 之后 B 仍写不动** → 伪造路径换不来越权。

### 3.6 审计与事件流（面向 agent 的两个通道）

| | 审计 JSONL | `--json` 事件流（stdout） |
|---|---|---|
| 写入方 | `core/audit.rs:18`（Unix）/ `win/audit.rs:18` | `core/state.rs:100 emit_event` |
| 面向 | 事后审计与追溯 | **agent 实时消费** |
| 内容 | 事件类型、路径、`precision`、`source`（`explicit`/`sandbox-log`）、`attributed` | `spawned`/`exit`/`violation`/`violation.captured`/`escalation.*`/`token.*`/`retry`/`proxy.*`/`sid`/`network` |

> 三平台的**事件名集合必须严格一致**——这由 `contract-baseline.json` 的
> `event_names_allowed` / `audit_events_allowed` / `event_names_required` 保证，
> 由**同一份** `scripts/contract_check.py` 在三平台各跑一遍。

### 3.7 生命周期与清理

任务结束必须**不留痕**：撤销 ACL（`win/acl.rs:79 revoke`）、回收空占位文件、
撤回回环例外、关闭 Job/token/管道句柄、杀掉整个进程组（Unix `kill(-pgid)`）。
`T10d` 断言「任务结束无提权 ACL 残余」，`T10c` 断言「宿主被杀后无残留沙箱进程」。

## 4. 各系统的实现原理（逐系统）

### 4.1 策略与契约（`crates/aisbx-policy`）

`Policy` 是唯一契约；`deny_unknown_fields` 让拼错的键**必须失败**而不是被忽略。
三平台的期望值差异（能力报告里的平台期望）写在 `contract-baseline.json` 的 `platform_expect`，
**值可以按平台不同，结构不能不同**。

### 4.2 启动器与重试循环（`unix/run.rs` / `win/run.rs`）

- Unix：起 broker（UDS：`esc.sock`/`ctl.sock`/`net.sock`）→ 每轮生成 argv → `spawn`（`setpgid(0,0)` + stderr 管道 + `RLIMIT_AS`）
  → 采集 violation → 等待授权 → 把授权路径并入快照 → 重跑（≤N 轮）→ 收尾回收。
- Windows：生成 package SID → 展开路径 → 白名单 ACL → 回环例外 → LowBox token → Job →
  broker 双管道 + 宿主代理 + 注入代理环境变量 → **挂起创建 → 入 Job → 恢复** → L1 采集 → 授权等待 → 重跑（≤3 轮）→ 撤 ACL/回收。

### 4.3 macOS 后端（Seatbelt + L2 内核日志）

- `macos/seatbelt.rs:17`：按策略生成 SBPL profile；`argv():85` 组装 `sandbox-exec -p <profile> -- <cmd>`。
  `sandbox-exec` 不存在即拒绝执行（fail-closed，`:86-88`）。
- `macos/violations.rs:104`：**L2** 采集——从内核日志里读 `sandbox-reporting-violation` 事件，
  解析出**真实**被拒路径 → `precision=exact`。

### 4.4 Linux 后端（bubblewrap）

- `linux/bwrap.rs:21`：生成 `bwrap` 参数（`--bind` / `--ro-bind` / `--unshare-net` / `--die-with-parent` 等）。
  `bwrap` 不存在即拒绝执行（fail-closed，`:22-24`）。
- 授权「尚不存在的文件」：占位文件 + 单文件 bind + 结束回收（见 3.3）。
- Landlock/seccomp 随 bwrap 生效 → 能力报告里标 `partial`。

### 4.5 Windows 后端（AppContainer + Job + ACL）

- **package SID**：`win/token.rs:44` 用 `DeriveAppContainerSidFromAppContainerName` 推导
  （**不能自己拼 `S-1-15-3-*`**，那是 capability SID，传给 `NtCreateLowBoxToken` 会 `STATUS_INVALID_PARAMETER`）。
  走 `Derive…` 而非 `CreateAppContainerProfile`：不写注册表、零残留、亚毫秒。
- **LowBox token**：`win/token.rs:103`：`DuplicateTokenEx` → `NtCreateLowBoxToken(package_sid, caps)` →
  `SetTokenInformation(TokenIntegrityLevel, S-1-16-4096)` 降到 Low 完整性。
  **caps 为空 ⇒ 沙箱无任何网络 capability**。
- **进程创建**：`win/proc.rs:95` `CreateProcessAsUserW(lowbox, …, CREATE_SUSPENDED)`；
  `lpEnvironment=NULL` ⇒ 继承宿主环境 ⇒ 靠设置 `HTTP_PROXY` 注入代理（`run.rs:346`）。
  **顺序**：挂起创建 → `AssignProcessToJobObject` → `ResumeThread`（先入 Job 再恢复）。
- **ACL**：`win/acl.rs` 全部用 `icacls /grant` **追加** ACE（不破坏宿主原权限）；
  `grant_path_precise:56` 四分支：目录 / 已存在 / 不存在+写（占位文件+文件级 M）/ 不存在+读（父目录继承 RX）。
- **Job**：`win/job.rs` 提供内存总量、单进程内存、进程数、CPU 限制，并保证进程树随 Job 终止。
- **管道**：`win/broker.rs:227-307` 用 SDDL + **手写 Low 完整性标签**（`SYSTEM_MANDATORY_LABEL_ACE_TYPE=17`），
  否则低完整性子进程一律 `ACCESS_DENIED`；写 SACL 需 `AdjustTokenPrivileges` 启用 `SeSecurityPrivilege`；
  `PIPE_REJECT_REMOTE_CLIENTS` 禁远程客户端。

### 4.6 broker 协议（平台无关的语义，两套实现）

单行 JSON（`core/protocol.rs:7 EscRequest` / `:28 Reply`）：
`esc.sock` 供沙箱内 `aisbx escalate`（Unix）/ 命名管道 `aisbx-<task>`（Windows）；
`ctl.sock` / `…-ctl` 供宿主 `authorize`/`status`。
Windows 的 `ctl` 管道 DACL 仅属主（`S-1-3-4`），**沙箱内即使同用户也过不了 AppContainer 附加检查**。

### 4.7 token 机制（`core/tokens.rs`）

一次性、绑定 **path + access + TTL**，兑换即消费（`redeem`），重放被拒（`token.reject`）。
Windows 侧镜像实现于 `win/broker.rs`（`IssuedToken`/`redeem_token`）。

### 4.8 契约检查机制（`scripts/contract_check.py` + `scripts/contract-baseline.json`）

三平台**共用同一份脚本与基线**，各跑 19 项：能力报告顶层结构 / 能力键集合**严格相等** /
值域 / 平台期望 / `--json` 事件流事件名 / 平台无关事件齐备 / 审计事件类型 / 退出码语义。

- 平台名取自能力报告的 `backend`（**不能写死**——写死会让 macOS 拿 Linux 的期望去比，实测踩过）。
- 退出码约定：`0` 成功 / `1` 被拒 / `2` 用法或环境错 / `3` 等待授权超时 / `99` 内部失败。
- 报告落盘（`--out` / `CONTRACT_REPORT_OUT`）→ 失败详情随 CI 结果回写，不依赖 GitHub API 配额。

## 5. 这套设计为什么「三平台同形」

1. **能力报告是结构化降级**：每个平台逐项如实标 `full/partial/unavailable`，
   消费方（agent）据此决策；`--require-full` 让不满足就**拒绝启动**而不是裸跑。
2. **契约检查共用一份**：结构一致性由 CI 保证，而不是靠约定。
3. **授权语义统一到「占位文件 + 单文件授权」**：macOS/Linux/Windows 在「授权一个尚不存在的文件」
   上曾经行为不同，已统一；这是「交互一样」的实质内容之一。
4. **两个采集通道分层声明**：L1（stderr 自报，`reported`）与 L2（内核日志，`exact`），
   能力报告里 `violation_file_path_precision` 与 `violation_log_probe` 如实区分，
   agent 因此知道**该不该信这个路径**。

> 待收口的一处不对称：Unix 的 `Deny` 模式仍会空等到超时，Windows 立即退出（见 3.2 末）。
