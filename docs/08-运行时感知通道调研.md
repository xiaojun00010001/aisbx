> 并重读 Codex / Claude Code 在这个场景下的真实实现机制。

## 0. 结论速览

1. **用户判断成立，且是因果关系不是偏好**：感知精度决定「重跑」这个动作的
   爆炸半径。感知不到路径 → 只能请求「整条命令豁免沙箱」→ 用户签的是
   「这条命令随便跑」；感知到路径 → 只扩一个文件。**Codex 之所以给出
   `retry without sandbox` 这种粗粒度选项，正是因为它拿不到精确路径。**
2. **Codex 的「更宽松的策略重跑」分两档，不能混为一谈**（见 §1.1）：
   `require_escalated` = 整条命令**退出沙箱**；`writable_roots` = 沙箱内扩写，
   但**配置期**、不是运行中按需。
3. **Claude Code 在文件侧也没有稳定的精确路径**：srt README 自述
   「文件系统操作通常仍表现为原生命令错误，例如 `EPERM`」「Linux seccomp
   主要提供 syscall 级信息，不保证能还原具体文件路径」。它对网络做到了精确
   （宿主代理在数据路径上），对文件没有。
4. **五层感知通道模型**（§2）：能做到「不解析、不猜测」的只有 L1（程序自报）、
   L2（内核日志）、L3（数据路径必经点）；L4（内核同步裁决）才能「运行中放行」。
   **感知用于「问」，内核裁决用于「放」**——这条分界决定了本轮的实现取舍。
5. **本轮实施**：macOS 归属从「入口 PID」升级为「PID 集合 + 进程组反查」，
   实测把漏采与误判都收敛；并把「未能归属」与「越界」在数据模型上彻底分开
   （新增 `precision` / `attributed` 两个正交维度）。
6. **本轮暴露并修掉一个真实越权风险**：`com.apple.sandbox.reporting` 里
   **混着同机其它应用的违规**（实测捞到 Chrome 的 `libsoda.so`、`wifip2pd`）。
   未能归属的条目若当成越界，就会去要用户授权无关路径，且能被用来伪造
   「真实拒绝」骗过 token 签发。现在它们只进审计。
7. **方向修正（用户明确）：运行中放行不是必须机制，重试执行同样可以。**
   于是三平台主线统一为「**感知 → 授权 → 重跑**」。Windows 侧原先
   `launcher_retry: unavailable`——授权后 agent 重跑仍被拒（token 跨 run 不延续）
   → 死循环,这是真实可用性缺陷;本轮补齐后 `effect` 由
   `in-place(legacy)+agent-retry` 改为 `retry`,三平台契约一致。
8. **Linux 侧「内核给的精确路径」目前无路可走(已调研、暂不实施)**:Landlock 6.15
   audit 需 ≥6.15 内核(本机与 CI 都不满足)、auditd 违背「无需管理员」原则、
   seccomp `USER_NOTIF` 成本过高。按「不假装」原则不盲写,把结论与**触发条件**固化。
   顺带澄清:**L1 的可伪造性在沙箱语义下不构成越权**(授权对象 = 被授权对象,
   程序撒谎也拿不到超出批准的权限);真正放大授权范围的是**授权落地方式**——
   已把 Windows 的「授父目录 Modify」收紧为「授父目录 `(AD)` 仅可新建」。

## 1. 竞品机制重读（一手来源）

### 1.1 Codex：两档「重跑」，官方文档明确区分

来源：OpenAI《Configuration Reference》《Agent approvals & security》、
《Building a safe, effective sandbox to enable Codex on Windows》。

| 机制 | 沙箱还在吗 | 精确到路径吗 | 时机 | 作用域 |
|---|---|---|---|---|
| `require_escalated`（UI 文案 **"retry without sandbox"**，官方称 *full sandbox escalation*） | ❌ **整条命令脱离沙箱边界**，在当前账户权限下跑 | ❌ 不感知路径 | 运行中（失败后） | 单条命令 |
| `sandbox_workspace_write.writable_roots` | ✅ 沙箱内，只多开放指定目录 | ✅ 精确路径列表 | **配置期**（`config.toml`） | 会话 |
| `sandbox_workspace_write.network_access` | ✅ 沙箱内 | ✅ 精确域名 | 配置期 | 会话 |

官方原话：

> **"A narrow network grant is different from full sandbox escalation."**

> 若审批框明确写的是 "retry without sandbox"，**不要把它理解为「只补一个缺失
> 权限」**；审批前检查完整命令及其副作用。

其它要点：

- 沙箱拒绝的识别靠 **stderr 特征**（`"Operation not permitted"` /
  `"bubblewrap is unavailable"`）与退出码，**不做精确路径采集**；
- `approval_policy = "never"` 只是不弹提示，**不会扩大沙箱权限**；
  `--yolo` / `danger-full-access` 才是会话级无沙箱；
- Linux 是 **bubblewrap + Landlock + seccomp 三层**，Landlock
  `restrict_self()` 后检查 `RulesetStatus::NotEnforced`，内核不支持即拒绝执行；
- **Windows 不用运行中改 ACL**。官方文章明确列出 ACL 方案的缺点（慢、留痕、
  语义变更成本高、**不适合做成类似 macOS 动态生成 `.sbpl` 的机制**），
  改为**配置期**用合成 SID `sandbox-write` + DACL 授权 `cwd` 与 `writable_roots`，
  运行期只建受限令牌（受限 SID 列表 `[Everyone, Logon, Synthetic]`），
  网络用专用账户 `CodexSandboxOffline/Online` + WFP。

> **对我们的意义**：Windows 上「客体侧改 ACL」确实能做运行中放行，但 Codex
> 评估后认为代价大到不值得。我们保留该能力（`win/acl.rs`），但要知道它比
> Codex 多付了什么成本。

### 1.2 Claude Code / `anthropics/sandbox-runtime`

来源：`anthropics/sandbox-runtime` README（一手）、官方 Sandboxing 文档。

- **网络**：宿主 HTTP/SOCKS5 代理在数据路径上，域名 allowlist + DNS
  rebinding 防护 + 可选 TLS MITM + **ask callback**；`--control-fd` 可热更新
  网络列表。**这是三家里唯一「运行中按域名放行」的实现**。
- **文件**：macOS 动态 SBPL；Linux bubblewrap + 预生成 seccomp BPF
  （禁 `unshare`/`setns`/`mount`/`umount2`/`pivot_root`、`clone3`→ENOSYS）；
  **README 明确说文件系统规则运行中不可变**。
- **违规采集**：`SandboxViolationStore`，来源 = *seatbelt log lines + seccomp
  events + proxy denies*，用 128bit `commandId` 归因；
  `annotateStderrWithSandboxFailures(key, stderr)` 把失败标注到命令 stderr 上。
- **README 自述的局限**（关键）：文件系统操作通常仍表现为原生命令错误
  （`EPERM`）；没有跨平台稳定的结构化字段保证返回原始文件路径；Linux seccomp
  不保证能还原具体文件路径。
- Windows 侧 srt 是 alpha（专用账户 + WFP + 受限令牌），Claude Code 原生
  Windows 则**不提供沙箱**（需 WSL2）。

### 1.3 DeepSeek Harness（dsh）

沙箱拒绝 → 请求用户同意 → **以更宽松 `sandboxPolicy` 重试**。Windows 用
`WRITE_RESTRICTED` token + 由工作区路径确定性派生的 Workspace Write SID；
网络明确标注 Not enforced。

### 1.4 横向对照

| | 文件侧精确路径感知 | 运行中放行 | 授权后怎么办 |
|---|---|---|---|
| Claude Code | ⚠️ 内核日志 + stderr 标注，**不保证稳定结构化** | 仅网络 ✅ | 文件重跑 / 网络热更新 |
| Codex | ❌ 仅 stderr 特征（连路径都不取） | ❌ | **整条命令出沙箱**（或配置期 `writable_roots`） |
| dsh | ❌ | ❌ | 换策略重试 |
| **aisbx（本轮后）** | ✅ macOS 内核日志（`exact`）<br>✅ Linux/Windows stderr 自报（`reported`） | ✅ 仅网络 | **补精确路径进策略快照 → 沙箱内重跑（三平台统一）** |

**aisbx 是唯一同时做到「运行中 + 精确路径 + 沙箱内」的**——而这个细粒度的
前提正是感知精度。

## 2. 五层感知通道模型

「能不能不解析、不猜测就拿到具体信息」——能，但分五层，代价差别巨大。

| 层 | 手段 | 拿到什么 | 特权 | 运行中放行 | 谁在用 |
|---|---|---|---|---|---|
| **L1** | 程序**自己打印**的路径 | 精确绝对路径 | 否 | ❌ | Codex（间接） |
| **L2** | 内核**被动日志** | 精确路径 + PID + 操作 | macOS 否 / Linux 需 auditd / **Windows 需管理员** | ❌ | Claude Code |
| **L3** | **数据路径必经点**（网络走代理） | 精确 host:port | 否 | ✅ | Claude Code |
| **L4** | 内核**同步裁决** | 精确路径 + 当场裁决 | macOS 需公证扩展 / Linux 免特权 / **Windows 需签名驱动** | ✅ | 无（空白） |
| **L5** | 用户态**拦截层**（FUSE / WinFsp） | 精确路径 + 自由裁决 | 需装驱动 | ✅ | 无 |

**L1 补充实测**（本轮，macOS 26.3）：Seatbelt 拒绝时，三个互不相同的程序
错误信息里都带精确绝对路径——

```
/bin/sh:  /Users/.../sbx-blocked.txt: Operation not permitted      exit=1
touch:    /Users/.../sbx-blocked2.txt: Operation not permitted      exit=1
python3:  PermissionError: [Errno 1] Operation not permitted: '/Users/.../sbx-blocked3.txt'
```

即：**路径是程序自己要访问的那个路径**（内核只回 `EACCES`，不带路径），
所以这不属于「猜测」，但**属于解析 stderr**，且混着启动噪声
（实测 python 启动就刷出 `/tmp/xcrun_db-*`、`/var/folders/*` 的拒绝）。
Windows 上还取决于运行时生态：.NET / PowerShell / Python 会带路径，
原生 C/C++ 工具通常只给一句 `Access is denied`。

### 核心原则：感知用于「问」，内核裁决用于「放」

| 通道 | 可信度 | 生成授权请求 | 自动放行 |
|---|---|---|---|
| L1 程序自报 | 中（**可伪造**） | ✅ | ❌ **绝对不行** |
| L2 内核日志 | 高 | ✅ | ❌ |
| L3 代理（协议自带） | 高 | ✅ | ✅ |
| L4 内核同步裁决 | 最高 | ✅ | ✅ |

L1 不能自动放行的理由：恶意程序可以自己打印一个无害路径骗过采集器，然后去
碰真正的目标——等于让被沙箱约束的程序自己给自己签发通行证。

**本项目核查结果**：`win/broker.rs::decide_file` 三档——黑名单 fail-closed →
token 快速路径（宿主签发 = 人已确认）→ 无 token 时走 `escalation_mode`
（`Deny`/`Auto`/`Prompt`，`Prompt` 会问人）。**没有「程序自报路径 → 自动落
ACL」这条缝**，唯一要盯的是 `Auto` 模式的 `allow_escalation` 前缀列表必须
保持为配置期预授权，不许采集器自动写入。

## 3. 本轮实施（P0）：归属精度改造

### 3.1 问题

原实现按「入口 PID + 登记 PID」归属内核日志行。实测三处漏采/误判：

| 实测（macOS 26.3） | 数据 | 后果 |
|---|---|---|
| 入口 PID vs 内核上报 PID | 入口 `64904`，日志 `64905`（= 入口 fork 出的子 shell） | 所有 fork 出来的子孙进程全漏 |
| 违规进程深度 | 入口 `84007`，日志 `84011`（**深 3 层**） | kqueue `NOTE_FORK` 只覆盖 1 层；递归注册永远慢一步；采样式 `ps` 快照在 12ms 的命令里根本来不及 |
| 日志落盘延迟 | 命令 12ms 结束 → `1467ms` 后日志可见 | 原 3×800ms=1.6s 窗口卡在边缘，是真实漏采源 |
| 同机其它应用的违规 | 捞到 Chrome `libsoda.so`、`wifip2pd` mach-lookup | 若当越界 → 要用户授权无关路径（越权） |

### 3.2 改动清单

| 文件 | 改动 |
|---|---|
| `unix/proctree.rs`（新增） | `snapshot_pgid()`（macOS `ps` / Linux `/proc`）、`pgid_table()`（pid→pgid 反查）、`ForkWatcher`（macOS `kqueue` `EVFILT_PROC`/`NOTE_FORK`/`NOTE_EXIT`，事件驱动、不漏短命进程）、`merge_pids()` |
| `unix/run.rs` | `spawn()` 改事件驱动等待：kqueue 收 fork 后代（覆盖入口的直接子进程）；**进程组回收 `kill(-pgid)` 从 spawn 内挪到采集之后**——否则违规进程已被我们杀掉，进程组反查永远失效；`SpawnOutcome` 增 `pgid`/`tree` |
| `macos/violations.rs` | 归属两级：①已知 PID 集合（入口 + kqueue 后代 + 登记 PID）②`pid→pgid` 反查（违规进程仍存活时，与深度无关）；两级都不成立 → `unattributed`；重试窗口 3×800ms → **8×400ms**；`--last 1m` → **`--start <命令开始时刻>`**（长命令不漏早期违规、减少无关扫描）；新增 `now_timestamp()` |
| `core/state.rs` | `Violation` 增两个正交维度：`precision`（路径精度 `exact`/`reported`/`none`）与 `attributed`（能否证明来自本次执行）；新增 `unattributed_file_violation()`：**只进审计，不进 violations 列表、不置 `needs_approval`** |
| `capabilities.rs` | 新增 `violation_file_path_precision` / `violation_net_path_precision`（macOS `exact`/`exact`，Linux/Windows `none`/`exact`）；`auto_violation_capture` 的 `partial` 理由更新 |
| `scripts/smoke-unix.sh` | 新增 T7f–T7l 共 8 项断言 |

### 3.3 关键设计：把「未能归属」与「越界」在数据模型上分开

```jsonc
// 归属成立 → 进 violations 列表,可驱动授权
{"event":"violation","kind":"file","path":"/x/y.txt","precision":"exact",
 "attributed":true,"source":"sandbox-log","reason":"needs-approval"}

// 归属不成立 → 只进审计,绝不驱动授权
{"event":"violation.unattributed","path":"/x/y.txt","attributed":false,
 "source":"sandbox-log","reason":"not attributable to this execution"}
```

配套的 fail-closed 断言（T7l）：**未归属条目不得用于申请授权**——
否则等于允许为「同机其它进程的违规」开权限，也能被用来伪造「真实拒绝」
骗过 token 签发（`has_real_violation` 是签发前置校验）。

未归属条目还按 `is_relevant_unattributed()` 过滤：我们的 profile 是
`(allow file-read*)`，读几乎不会被拒，故 **write 一律保留**；
**read 只有命中 profile 里显式 deny 的凭据目录**（`.ssh`/`.aws`/`.gnupg`/
`.kube`/`.docker`）才保留——这样能滤掉 Chrome 读自己 so 这类噪音。

### 3.4 采集时序（本轮标定）

```
命令启动 ──▶ since = now_timestamp()        ← 必须在 spawn 前取
        ──▶ spawn(事件驱动收集 fork 后代)
        ──▶ 命令结束(入口退出)
        ──▶ collect(): log show --start since
              第 1 次查询 ≈ 立即(日志未落盘,查不到)
              …重试,实测第 ≈1.5s 落盘后可见…
        ──▶ 归属判定(pid 集合 / pgid 反查)
        ──▶ kill(-pgid) 回收进程组          ← 必须在采集之后
```

### 3.5 验证结果

- `cargo test`：16 项全过（新增 6 项：ps 解析、`/proc` stat 切分、合并去重、
  未归属降级、pgid 反查归属）。
- `bash scripts/smoke-unix.sh`（本机 macOS 26.3）：**fail=0**，
  新增 T7f–T7l 全绿：
  - T7f 短命深层进程**不**作为越界上报（仅审计）
  - T7g 未归属条目仍留审计记录（路径可见）
  - T7i 存活的深层进程按进程组精确归属（`attributed=true`）
  - T7j 越界路径标注为内核来源且精确（`precision=exact`）
  - T7k 可归属的越界不重复出现在未归属列表
  - T7l 未归属条目**不得**用于申请授权
- `cargo check --target x86_64-pc-windows-gnu --all-targets`：通过
  （`core/state.rs`、`capabilities.rs` 的改动不影响 Windows 后端）。

### 3.6 顺带修掉的两个测试陷阱（值得记住）

1. **`serde_json::json!` 的 Map 是 BTreeMap，输出按【字母序】**
   （`access, attributed, command_id, event, path, pid, precision, reason, source`），
   不能假设 `"event"` 在 `"path"` 之前。grep 断言一律用管道、不依赖字段顺序。
2. **等待条件不能用「命令里出现的路径」**：`spawned` 事件的命令串里也含该
   路径，用它做等待条件会立刻 break，断言在采集完成前就执行了。必须等
   `violation` 事件。

## 4. P1 + P2 实施：L1「程序自报路径」通道（Unix + Windows）

### 4.1 为什么做它

L2（内核日志）路径精确，但只有 macOS 有；L1 补上 Linux / Windows 的空缺。
两者**互补**：L2 拿不到归属时（短命深层进程）由 L1 顶上，反之亦然。

### 4.2 实测：路径是程序自己拼的，不是内核给的

内核只回 `EACCES`（不含路径）。同一份 Seatbelt profile 下被拒：

| 程序 | stderr | 含路径 |
|---|---|---|
| `/bin/sh` | `sh: /path/x.txt: Operation not permitted` | ✅ |
| `touch` | `touch: /path/x.txt: Operation not permitted` | ✅ |
| `python3` | `PermissionError: [Errno 1] Operation not permitted: '/path/x.txt'` | ✅ |
| Rust（`burn`） | `write failed: Permission denied (os error 13)` | ❌ |

**结论**：L1 覆盖率取决于程序生态，不是 100%。Rust / Go / C 这类直接抛 `errno`
的运行时不会把路径拼进消息——这不是实现问题，是语言库的设计。

### 4.3 信任边界（本轮最关键的设计取舍）

| 维度 | L1（stderr 自报） | L2（内核日志） |
|---|---|---|
| 归属 | **确定**（stderr 来自本次执行的进程） | 需归属判定（可能降级为 unattributed） |
| 路径 | **程序自称，可伪造** | 内核给的，不可伪造 |

所以 L1 的 `precision` 恒为 `reported`、`attributed` 恒为 `true`。

**风险**：恶意程序可以 `echo "Operation not permitted: /etc/passwd" >&2`
骗过采集器，让宿主以为它需要这个路径。

**防线**：

1. L1 路径**只用于生成授权请求**，绝不自动放行（`precision=reported`）；
2. 授权环节必须有人参与——宿主 `authorize` 签发 token 前需用户/策略确认，
   审批框里展示的是**具体路径**，用户能判断合理性；
3. L1 **不走** broker 的 escalate 通道，故不会触发 `EscalationMode::Auto`
   的前缀自动授权；
4. L2 已采集到的路径不再由 L1 重复上报（L2 的路径更可信）。

### 4.4 实现

| 文件 | 改动 |
|---|---|
| `common/stderr_scan.rs`（新增，跨平台） | 解析器：同一行必须同时满足「有拒绝语义」+「有绝对路径」；引号路径优先，否则取**最后一个**绝对路径 token（第一个常是程序自身路径，如 `/bin/sh`）；系统噪声前缀过滤；**Windows 形态**：盘符 `C:\`/UNC `\\server` 识别、`.NET` 的 `Access to the path 'X' is denied.` 与 `UnauthorizedAccessException`、`C:\Windows` 等系统目录过滤、Python repr 的 `\\` 反转义；单测 10 项 |
| `common/mod.rs` | 由 `common.rs` 改为 `common/mod.rs` 以容纳跨平台子模块；新增 `path_prefix_hit()`（只统一分隔符与大小写，**不** canonicalize——Windows 的 `canonicalize` 会加 `\\?\` 前缀反而与 stderr 的字面路径对不上） |

### 4.5 已知副作用（如实登记）

- **stderr 被管道化**：`isatty(stderr)` 由真变假，程序可能改用行缓冲、隐藏进度条。
  仅在 `broker.violation_capture` 显式开启时发生；默认路径逐字节不变。
- **覆盖率依赖程序生态**（见 §4.2），Rust / Go / C 程序取不到路径。
- **`access` 是启发式**：多数错误消息不区分读写，按是否出现 "read" 推断。
- **Windows 侧 stdout 也被重定向**:`STARTF_USESTDHANDLES` 会同时接管三个标准句柄,
  因此 stdin 接到 `NUL`、stdout 接到父进程 stdout(经 `DuplicateHandle` 复制成
  可继承副本,父进程侧副本用完即关)。行为与继承一致,但多了一次句柄复制。

### 4.6 Windows 侧实现要点(句柄继承的安全核查)

Windows 要把 stderr 接到管道,就必须 `bInheritHandles=TRUE` + `STARTF_USESTDHANDLES`。
这意味着子进程会继承父进程**所有可继承**句柄——必须逐个确认不会泄漏控制通道:

| 句柄 | 可继承? | 处置 |
|---|---|---|
| broker 命名管道 | **否** | `bInheritHandle = 0`(`win/broker.rs` 已是)→ 沙箱内程序无法直接与宿主 broker 对话 |
| Job Object / LowBox token / 代理 socket | 否 | 默认不可继承 |
| 管道**读端** | **必须否** | 新增 `SetHandleInformation(read, HANDLE_FLAG_INHERIT, 0)`,否则子进程能读同一份数据与我们竞争 |
| 管道写端 / `NUL` / stdout | 是 | `NUL` 与 stdout 经 `DuplicateHandle` 复制成可继承副本,父进程侧副本用完即关 |

- Windows 冒烟(T11a–T11d)**需 CI windows-smoke 验证**:本机无 PowerShell 与
  Windows 内核,无法本地真机执行;已按「不假装验证过」的原则标注。

## 5. P3 实施：Windows 侧 B 契约重跑闭环

### 5.1 为什么做它(方向修正)

**运行中放行不是必须机制,重试执行同样可以**——这是本轮的方向修正。于是三平台
的主线统一为「**感知 → 授权 → 重跑**」,而 Windows 侧此前是:

- `effect: "in-place(legacy)+agent-retry"`、`launcher_retry: "unavailable"`
  → launcher 既不等授权、也不重跑;
- 后果:agent 在授权后重跑命令,**新 run 里授权不延续**(token 跨 run 不保留)
  → 又被拒 → 死循环。

这是 Windows 侧一个**真实的可用性缺陷**,而且在「重跑即可」的方向下,它是
三平台统一 B 契约的最后一环。

### 5.2 补齐的链路

```text
命令失败(写被拒)
  ↓ L1 采集到路径(stderr 自报)或沙箱内 escalate(Prompt 且无 TTY)
  ↓ 置 needs_approval
  ↓ launcher 轮询 granted_paths(最长 20s)
  ↓ 宿主 `aisbx authorize --path X --access write` → broker 签 token 并记入 granted_paths
  ↓ launcher 发现增长 → 把 X 并入本轮白名单(落 ACL)→ 重跑(最多 3 轮)→ 成功
```

与 Unix 侧 `unix/run.rs::run_loop` **逐条对齐**:同样的 `WAIT_AUTH_SECS=20`、
`MAX_ATTEMPTS=3`、只等「需要用户授权」的拒绝、其余失败(黑名单/策略拒绝)直接退出。

### 5.3 改动

| 文件 | 改动 |
|---|---|
| `win/broker.rs` | `BrokerHandle` 增 `granted_paths`(宿主已授权路径)与 `needs_approval` 标志;`handle_control` 的 issue 分支把路径记入 `granted_paths`;`decide_file` 的 Prompt 分支在**无 TTY** 时置 `needs_approval` 并返回「需要用户授权后重新执行」(有 TTY 时仍就地交互问人,既有行为不变) |
| `run.rs`(Windows) | spawn/wait 段改为执行循环:每轮把已授权路径并入白名单并落 ACL → 执行 → 失败则等授权 → 授权到达则重跑;`spawned`/`exit` 事件带 `attempt`;新增 `retry` 事件 |
| `capabilities.rs` | Windows `effect`:`in-place(legacy)+agent-retry` → **`retry`**;`authorized_retry`/`launcher_retry`:`partial`/`unavailable` → **`full`**/`full` |
| `examples/burn.rs` | `stderrdeny` 改为**真的尝试写**:被拒 → 打印带路径的 .NET 形态消息;被授权 → 写成功退出 0 → 「拒绝→授权→重跑」是真实链路,不是演出来的 |
| `scripts/smoke.ps1` | 新增 T12a–T12c(授权后重跑成功 / 文件真实落盘 / retry 事件已落审计) |

### 5.4 已知边界(如实登记)

- **Windows 侧仍未本地真机验证**:本机无 Windows 内核与 PowerShell,
  T11/T12 只做了交叉编译验证,由 CI `windows-smoke` 承担。
- **in-place 放行保留为 legacy 加速路径**:broker 收到 token 即落 ACE,运行中的
  进程立刻可用。它与重跑**不冲突**——in-place 生效后命令若已成功,本轮
  `code==0` 直接退出,不会重跑。
- **授权路径可能尚不存在**(被拒的正是「要创建的文件」):`grant_path` 改为对
  父目录授可继承 ACE;撤销时撤销的是**实际落 ACE 的那个目标**,不留残余。
- **Windows 的 `is_tty()` 是启发式**(`TERM`/`SESSIONNAME` 环境变量探测)。
  误判为「有 TTY」时会尝试交互问人并读 stdin;无头环境读 stdin 立即 EOF,
  不会挂起,但会多一次失败的交互。

- `cargo check --target x86_64-pc-windows-gnu --all-targets`:**0 error / 0 warning**
- `cargo test`:28 项全过(Unix 侧未受影响)
- Unix 冒烟 **fail=0**(未回归)
- Windows 的 T11/T12 **需 CI 验证**(本机无 Windows 内核,未本地真机执行)

## 6. P4：Linux 精确路径的可行性结论 + Windows 授权粒度收紧

### 6.1 Linux 侧拿「内核给的精确路径」：三条路与各自的硬约束

| 方案 | 精确度 | 归属 | 特权 | 当前环境可验证？ | 结论 |
|---|---|---|---|---|---|
| **Landlock 6.15 audit** | `exact` | **天然确定**：per-process（进程自己 `restrict_self`，内核 audit 子系统只记录它的 Landlock 事件） | 免特权 | ❌ 需内核 ≥ 6.15；本机 macOS、CI ubuntu-latest（6.8/6.11）都不满足 | **暂不实施**，等有 ≥6.15 的 runner |
| **auditd AVC** | `exact` | 需反查 pid→pgid（`/proc`），短命进程仍会漏 | **需 root + 改全机审计策略** | ❌ 违背项目「无需管理员」原则 | **不采用** |
| **seccomp `USER_NOTIF`** | `exact` | 天然确定 | 免特权 | 理论可行 | 成本过高：BPF 过滤 + 读用户态路径指针（TOCTOU）+ 代开文件（`ADDFD`）；且只能拦写类 syscall 才不至于拖垮性能 |

补充事实：Landlock 6.15 有个已知 bug——`get_current_exe()` 在 exe 路径过长时返回
`ENAMETOOLONG`，导致 `landlock_restrict_self()` 失败。真要用必须处理。

**结论**：Linux 侧的 `exact` 目前**没有一条既免特权、又能被当前环境验证的路**。
按项目「没有真机验证过的能力不标 full、不假装安全」的原则，本轮**不盲写**这条
通道，而是把结论与**触发条件**固化在这里：出现 ≥6.15 内核的 runner 时优先做
Landlock audit。

### 6.2 顺带澄清：L1 的「可伪造性」在沙箱语义下**不构成越权**

L1 的路径由程序自称，看似可伪造。放进沙箱语义里推一遍：

- 采集到路径 P → 展示给用户 → 用户同意 → 授权 P；
- 程序随后若去访问 Q：
  - Q ⊆ 授权范围 → 允许（用户批准的就是这一带）；
  - Q ⊄ 授权范围 → **内核照旧拒绝** ✓ 沙箱边界没变。

即**无论程序怎么撒谎，拿到的权限都不超过用户批准的路径**——因为授权对象与被
授权对象是同一个东西。L1 的缺陷是「路径可能不是它真正想要的」，**不是**「能拿到
超出授权的权限」。

**已用对抗用例实测证实**（`burn spoof <自称路径> <真实路径>`，断言 T15a–T15c）：
程序先真实写 `actual`（被内核拒绝），再向 stderr 打印一个**自称的** `claimed`：

| 断言 | 结果 | 说明 |
|---|---|---|
| T15a 内核通道采到**真实**被拒路径（`precision=exact`） | ✅ | L2 采的是内核确认的路径，**不受程序欺骗** |
| T15b 自称路径仅由 stderr 自报（`precision=reported`） | ✅ | L1 只能采到程序想让你看到的那个 |
| T15c **授权自称路径后，真实路径仍被拒** | ✅ | **伪造换不来越权**——核心结论被实测钉死 |

即：L1 会把「谎报」的路径交给 agent，但授权它并不能打开真实目标；真实目标仍由
内核挡着。而在有 L2 的平台上，同一次越界会**同时**出现两条（真实路径 `exact` +
自称路径 `reported`），agent 拿 `precision` 就能分辨该采信谁。

⚠️ 顺带修掉一个**真实缺陷**：L1 的系统噪声过滤原先把 `/var/folders/` 整个目录
当作噪声前缀——而 macOS 的 `TMPDIR` 正在 `/var/folders/…`，用户的真实目标也常落在
那里 → **L1 通道在这些路径上整个失灵**（实测：对抗用例的 `claimed` 一度采不到，
因为它在 `TMPDIR` 下）。现改为只匹配具体噪声形态（`/com.apple.`、`xcrun_db`），
并补两项单测钉住。**教训**：噪声过滤不能用「目录前缀」这种粗粒度规则，
否则用户数据与系统噪声无法区分。

⚠️ 真正会放大授权范围的**不是感知**，而是**授权落地方式**：用户批准「创建文件 X」，
若落地时对父目录授 Modify，实际给出的是「改/删该目录下所有文件」。这正是
§6.3 修掉的东西。

### 6.3 Windows 授权粒度收紧（本轮实施）

旧实现：目标文件不存在时，对**父目录授 Modify** → 授权范围 > 用户所见。
Unix 侧不存在这个问题（bwrap 只 `--bind` 目标路径本身）。

现改为 `win/acl.rs::grant_path_precise`：

- 目标是目录 → 授该目录；
- 目标是已存在文件 → 授该文件；
- 目标不存在 → 授**父目录的 `(OI)(CI)(AD)`**（Add Files/Add subdirectories）：
  只能**新建**，不能修改/删除已有内容。

权衡：若要做到「只允许创建、不允许创建子目录」，需用 SDDL 的 `FILE_ADD_FILE`(0x2)
且**不继承**，代价是新建文件不再继承 ACE（「先建后写」的少见写法会失败）。当前取 (AD)。

新增 Windows 断言 T13a–T13c（`burn probe2`：一次 run 内先试新建、再试同目录既有文件）：

- T13a 授权后新文件创建成功
- T13b **同目录既有文件仍不可写**（授权粒度不外溢）
- T13c 既有文件内容未被改动

## 7. agent 集成契约:`aisbx status` 的统一结构

### 7.1 为什么补这个

B 契约闭环里,agent 需要回答三个问题:

1. 有没有越界需要我处理? → `needs_approval`
2. 具体是哪条路径 / 哪个主机? → `pending[]`(带 `precision` / `attributed`)
3. 授权生效了吗? → `granted_paths` / `granted_nets`

此前:Unix 的 status 只给**数量**(`violations: N`),Windows 更是直接返回
`{"backend":"windows","status":"ok"}` —— 什么都没查。agent 只能去翻审计 JSONL 人工找路径,
或者干脆放弃「精确到路径」这件事。

现在两个平台返回**同一套字段**:

```json
{
  "backend": "unix",
  "attempt": 1,
  "retries": 0,
  "needs_approval": true,
  "pending": [
    {"kind": "file", "path": "/x/y.txt", "access": "write", "host": "", "port": 0,
     "source": "explicit", "precision": "reported", "attributed": true}
  ],
  "granted_paths": [],
  "granted_nets": [],
  "violations_total": 2
}
```

`precision` 与 `attributed` 必须一起透传给用户:`precision` 说明路径是内核给的
(`exact`)还是程序自称的(`reported`);`attributed=false` 时多半是同机其它进程,
**不应据此授权**。

### 7.2 agent 的标准流程

```text
1) 启动   aisbx run -p policy.json --json -- <命令>        (后台)
2) 轮询   aisbx status -p policy.json
            needs_approval == true → 读 pending[]
            按 precision / attributed 决定如何呈现:
              exact                → 「内核确认需要访问 /x/y」
              reported             → 「程序声称需要访问 /x/y(路径由程序自报)」
              attributed == false  → 不应据此授权(多半是同机其它进程)
3) 授权   aisbx authorize -p policy.json --path /x/y --access write
4) 重跑   run 自动以更宽的策略快照重跑(≤3 轮),直到 exit
5) 收尾   从 --json 事件流读 spawned / exit / retry / violation
```

### 7.3 实现与验证

- `common/pending.rs`:跨平台的 `PendingViolation`
  (**注意**:Windows 下没有 `core` 模块(`#[cfg(unix)] mod core;`),故必须放 `common`)
- `core/state.rs`:`State::pending()` 只取 `reason == "needs-approval"` 的条目
  —— 黑名单拒绝、策略拒绝**不该拿去问用户**(问了也是白问,策略已经定了)
- `unix/broker.rs`:status 分支返回新结构
- `win/broker.rs`:`BrokerHandle` 增 `pending` / `attempt` / `retries` 共享状态,
  控制通道新增 `status` 操作;新增 `status_client`
- `main.rs`:Windows 的 status 从「打印假 JSON」改为**真实查询**
- 新增 Unix 断言 T14a–T14c:status 给出具体路径 / 标注精度与归属 / 报告 `needs_approval`

**一个实测踩坑**:等待条件不能只看 `"pending"` 字段**存在**——它恒存在(空数组也匹配),
必须判断**非空**,否则第一次查询就 break,断言在数据到达前就跑了(第一版就是这么红的)。
