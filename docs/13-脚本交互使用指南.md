# 13 · 脚本交互使用指南（P1 高层接口）

> 更新日期：2026-11-21 · 适用版本：含 P1（`status.id` / `approve` / `guard`）与内核加固的当前 main。
> 目标读者：**编写脚本或 agent 集成 aisbx 的开发者**。
> 本文只讲「怎么用命令交互」，机制原理见 `docs/08`，逐条实测输出见 `docs/09` §14/§15，
> 易用性优化背景见 `docs/11`。

---

## 0. 三种交互层级（按推荐度）

| 层级 | 命令组合 | 适用场景 | 脚本复杂度 | 平台支持 |
|---|---|---|---|---|
| **L3 高层（推荐）** | `guard --approve-cmd <回调> -- <cmd>` | 一条命令跑完，回调决定授权 | 最低（1 条命令 + 回调脚本） | Linux/macOS 完整；Windows 重跑缺环境变量，按能力跳过 |
| **L2 中高层** | `status` → `approve --pending <id>` | agent 自己控制审批时机/UI | 中（轮询 + id 提取） | 三平台完整 |
| **L1 底层（兼容）** | `run`（后台）→ `status` → `authorize --path/--host` → `wait` | 需要精确控制 broker 生命周期 | 高（4 步 + 进程管理） | 三平台完整 |

> 约定：**运行时审批能力不是所有环境都能实现，不强求**。L3 在 Windows 上因后端未注入
> `AISBX_POLICY_FILE`/`AISBX_CLI`（`unix/run.rs:323-328` 有、Windows 无）无法重跑，
> 应降级到 L2 或按能力跳过，不要把失败记为产品缺陷。

## 1. 前置：策略文件模板

无论哪一层，都需要一份策略 JSON。最小可用模板（写白名单 + prompt 授权）：

```bash
cat > policy.json <<'EOF'
{
  "task": "my-task",
  "filesystem": {
    "write": ["/absolute/workspace"],
    "read": [],
    "deny_escalation": [],
    "allow_escalation": [],
    "escalation": "prompt"
  },
  "network": { "loopback": true, "internet": false },
  "resources": {},
  "broker": { "audit_log": "/absolute/audit.jsonl", "violation_capture": true }
}
EOF
aisbx policy-check -p policy.json
```

关键字段：
- `task`：只允许字母数字、`-`、`_`（用于 broker 管道/SID 名），**写脚本时必须唯一**。
- `escalation`：`prompt`（无 TTY → 邀请宿主授权）、`auto`（按 allow 前缀放行）、`deny`（终态拒绝）。
- `write`：可写白名单，绝对路径；授权成功后会以**单文件快照**并入（`docs/08` B 契约）。
- `deny_escalation`：不可授权黑名单，优先于一切 token（fail-closed）。
- `violation_capture`：是否启用内核日志/代理感知通道。

## 2. L3 · `guard`：一条命令完成授权闭环

### 2.1 审批回调协议

`--approve-cmd <exe>` 指向一个可执行文件，框架在检测到 actionable pending 时：

1. 把该 pending 的 JSON（含 `id`/`grant`/`precision`/`attributed`）写到回调的 **stdin**；
2. 读回调的 **stdout**，仅当 `trim()` 后等于 `approve` 才授权；其它任何输出/非零退出都视为拒绝；
3. 同一 `id` 只处理一次，避免重复授权。

### 2.2 最小回调（无条件同意，仅用于演示）

```bash
cat > /tmp/approver.sh <<'EOF'
#!/bin/sh
cat > /dev/null          # 消费 stdin 的 pending JSON
echo approve             # 生产环境应解析 JSON 自行决策
EOF
chmod +x /tmp/approver.sh

aisbx guard -p policy.json --approve-cmd /tmp/approver.sh -- \
  ./burn retryflow ./out/x.txt grant
```

实测输出（节选）：

```text
first_write=denied
{"granted":false,"reason":"需要用户授权后重新执行","effect":"retry","retry_required":true}
{"access":"write","granted":true,...}          # guard 自动调用回调
{"event":"retry","from":1,"to":2,"reason":"user-approved"}
wrote=ok
```

退出码 `0`、文件内容 `x`、token 重放仍被拒（`redeem=0 replay=1`）。

### 2.3 生产级回调（按精度/归属/路径决策）

```bash
cat > /tmp/approver.py <<'PY'
#!/usr/bin/env python3
import json, sys
p = json.load(sys.stdin)
# fail-closed：未归属、非 exact 精度、黑名单路径一律拒绝
if not p.get("attributed"):
    sys.exit(1)
if p.get("precision") not in ("exact", "reported"):
    sys.exit(1)
path = p.get("path", "")
if "/etc/" in path or "/.ssh/" in path:
    sys.exit(1)
print("approve")
PY
chmod +x /tmp/approver.py
```

回调 stdin 示例：

```json
{
  "kind": "file", "path": "/tmp/work/out.txt", "access": "write",
  "host": "", "port": 0, "precision": "reported", "source": "explicit",
  "attributed": true,
  "id": "f-9a3c1d0e",
  "grant": { "kind": "file", "path": "/tmp/work/out.txt", "access": "write", "ttl_seconds": 300 }
}
```

### 2.4 无回调 = 不放行

```bash
aisbx guard -p policy.json -- ./burn retryflow ./out/deny.txt grant
# 目标文件不会被创建（fail-closed，退化为普通 run，不自动放行）
```

## 3. L2 · `status` + `approve`：agent 自控制审批

### 3.1 流程

```bash
# 1) 后台起 run
aisbx run -p policy.json --json -- ./burn retryflow ./out/x.txt grant > run.out 2>&1 &
RUN_PID=$!

# 2) 轮询 status，提取 actionable pending 的 id
for i in $(seq 1 100); do
  ST=$(aisbx status -p policy.json)
  ID=$(printf '%s' "$ST" | python3 -c '
import json,sys
d=json.load(sys.stdin)
p=[x for x in d.get("pending",[]) if x.get("attributed")]
print(p[0]["id"] if p else "")' 2>/dev/null)
  [ -n "$ID" ] && break
  sleep 0.2
done

# 3) 按 id 授权（不必手工拼 --path/--host）
aisbx approve -p policy.json --pending "$ID"

# 4) 等重跑完成
wait "$RUN_PID"
```

### 3.2 `status` 输出字段

| 字段 | 含义 |
|---|---|
| `attempt` | 当前执行轮次（1 起） |
| `backend` | 后端名（`unix` / `windows` / …） |
| `needs_approval` | 是否有需要宿主授权的 pending（**网络授权时为 false**，见下） |
| `pending[].id` | 稳定标识，按 `summary()` FNV 派生，不随数组顺序变化 |
| `pending[].grant` | 可直接回填 `approve` 的授权参数 |
| `pending[].kind` | `file` / `net` |
| `pending[].precision` | `exact`（内核/协议自带）/ `reported`（程序自称，可伪造）/ `none` |
| `pending[].attributed` | 是否归属到本次执行；**false 不驱动授权** |
| `pending[].source` | `sandbox-log` / `stderr-selfreport` / `proxy` / `explicit` |
| `retries` / `violations_total` | 重跑次数 / 累计违规数 |

> ⚠️ **网络授权不要用 `needs_approval` 判断**：网络代理观测到目标时
> `needs_approval=false`（不触发重跑，运行中即时生效），但 `pending[]` 有 `kind:"net"`。
> 文件授权才看 `needs_approval=true`。

### 3.3 `approve` 的 fail-closed

- 不存在的 id → 非 0 退出，并列出当前 pending ids；
- `attributed=false` 的项 → 拒绝授权；
- 已授权的 id 再次 approve → 仍可用（幂等授权），但 token 一次性、重放会被 broker 拒绝。

## 4. L1 · 底层 `authorize`：兼容旧脚本

```bash
# 文件授权（目录级 / 单文件）
aisbx authorize -p policy.json --path /abs/target --access write --ttl-seconds 120

# 网络授权（按代理真实观察到的 host:port，运行中即时生效、不重跑）
aisbx authorize -p policy.json --host example.com --port 443

# 无真实越界时授权网络 → fail-closed 拒绝
```

`authorize` 直接对 broker 操作，不经过 `status.id`。适合已经自己解析审计日志、
只需要签发授权的老脚本。新脚本建议改用 L2/L3。

## 5. 沙箱内主动请求：`escalate`

被沙箱内的程序调用，向 broker 请求授权（不是宿主端命令）：

```bash
aisbx escalate -p policy.json --path /abs/target --access write
aisbx escalate --op net --host example.com --ip 1.1.1.1 --port 443   # Unix only
```

应答 JSON：

```json
{"granted":false,"reason":"需要用户授权后重新执行","effect":"retry","retry_required":true}
```

| effect | 语义 |
|---|---|
| `none` | 终态拒绝，不邀请宿主 |
| `retry` | 需要宿主授权后用新策略快照重跑（`granted:false` 也可能是这个语义，看 `retry_required`） |
| `in-place` | 运行中即时生效（网络授权） |

> Windows 后端未封装 `--op net`（入口即报错），按能力不强求。

## 6. 退出码语义

| 命令 | 退出码 | 含义 |
|---|---|---|
| 全部 | `0` | 成功 / 授权成功 |
| 全部 | `1` | 被拒 / 授权被拒 / 运行失败 |
| 全部 | `2` | 参数错误 / 未知子命令 |
| `run` | `3` | 等待授权超时（20s） |
| `approve` | 非 0 | id 不存在 / 未归属 / broker 不可达 |

脚本中务必区分「被拒（1）」与「参数错（2）」，不要把 2 当成策略拒绝。

## 7. 三平台差异速查

| 能力 | Linux | macOS | Windows |
|---|---|---|---|
| `status.id` / `approve` | ✅ | ✅ | ✅ |
| `guard` 文件重跑闭环 | ✅ | ✅ | ⚠️ 缺 `AISBX_POLICY_FILE` 注入，按能力跳过 |
| 文件越界感知精度 | `reported`（stderr 自报） | `exact`（内核日志） | `reported` |
| 网络授权即时生效 | ✅ | ✅ | ✅ |
| `escalate --op net` | ✅ | ✅ | ❌ 入口报错 |
| 内核加固（cap-drop/seccomp/proc） | ✅ | 不适用 | 不适用 |

用 `aisbx capabilities` 查询当前平台的真实能力，`--require-full` 可在启动前拒绝能力不足的环境。

## 8. 完整示例：agent 侧授权循环（L2 + L3 混合）

```bash
#!/usr/bin/env bash
set -u
BIN=aisbx
POLICY=policy.json

$BIN capabilities --json | python3 -c 'import json,sys; d=json.load(sys.stdin); assert d["capabilities"]["launcher_retry"]=="full"' \
  || { echo "当前环境不支持重跑闭环，跳过"; exit 0; }

# 优先 L3
if $BIN guard -p "$POLICY" --approve-cmd /tmp/approver.py -- "$@"; then
  exit 0
fi

# L3 不可用则降级 L2（手动轮询 + approve）
$BIN run -p "$POLICY" --json -- "$@" > run.out 2>&1 &
PID=$!
for i in $(seq 1 150); do
  ID=$($BIN status -p "$POLICY" | python3 -c '
import json,sys
d=json.load(sys.stdin)
p=[x for x in d.get("pending",[]) if x.get("attributed")]
print(p[0]["id"] if p else "")' 2>/dev/null)
  [ -n "$ID" ] && { $BIN approve -p "$POLICY" --pending "$ID"; }
  kill -0 "$PID" 2>/dev/null || break
  sleep 0.2
done
wait "$PID"
```
