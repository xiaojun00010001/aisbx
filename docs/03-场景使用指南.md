# 03 · 场景使用指南：越界识别、授权回传与资源限制观测

本文回答 agent 框架接入时最关心的三个问题：

1. 默认隔离下，程序访问了非授权文件——**沙箱怎么识别、agent 怎么拿到"具体是哪个路径"**；
2. 默认网络下，程序访问了非授权网络地址——**怎么识别、agent 怎么拿到"具体是哪个地址"**；
3. 资源限制（CPU / 内存 / 磁盘）——**程序超限后会不会被发现、以什么形式暴露**。

所有行为均以当前实现代码为准，未实现的能力在 §4「现状边界」中如实列出。

---

## 0. 一张总表：三个场景的判决与回传

| 场景 | 判决点（PEP） | 程序侧表现 | agent 拿到什么（`aisbx status`） | 授权后 |
|---|---|---|---|---|
| 文件越界 | Windows：内核 ACL（package SID 白名单）<br>macOS：Seatbelt SBPL<br>Linux：bubblewrap 只读根 + bind | 权限错误（Windows `ERROR_ACCESS_DENIED (5)` / macOS `Operation not permitted` / Linux `Permission denied`） | `pending[]`：**具体 path + access**，并带 `precision`（`exact`/`reported`）与 `attributed` | 补进策略快照 → **沙箱内重跑**（≤3 轮） |
| 网络越界 | Windows：无 internet capability<br>macOS：`(deny network*)`<br>Linux：独立 netns | 连接失败 | `pending[]`：**具体 host:port**，`precision=exact` | **运行中即时放行，命令不重跑**（代理侧，§2.4） |
| 资源超限 | Job Object（Win）/ rlimit（Linux）/ 无等价机制（macOS） | 逐维度不同（见 §3） | 退出码 / 进程创建失败错误；**运行中无水位上报**（见现状边界） | 不适用（限制不是授权问题） |

**三平台主线统一为「感知 → 授权 → 重跑」**（Windows 的运行中 in-place 放行保留为 legacy
加速路径）。文件侧因为路径由内核或程序自报，授权后走**重跑**；网络侧因为目标由代理的
CONNECT 报文自带，可做到**运行中放行而不重跑**。接入姿势见 §1.6。

---

## 1. 场景一：文件访问越界 → 识别 → 授权回传

### 1.1 默认行为：白名单外零配置拒绝

策略只声明 `filesystem.write`（Modify）与 `filesystem.read`（Read+Execute），宿主在任务开始时按 package SID 给这些目录挂 ACL（`win/acl.rs`）。白名单之外的任何路径——包括 `C:\ProgramData\ssh`、`%USERPROFILE%\.ssh` 这类敏感区——**不需要任何"拒绝规则"**，package SID 的令牌去打开它们时，内核 ACL 直接返回 `ERROR_ACCESS_DENIED`。

关键性质：这个判决发生在 **syscall 边界（内核 ACL 检查）**。无论路径来自模型参数、脚本拼接还是程序运行中自己算出来的，最终都要经过一次真实的 `CreateFile`，全部能被兜住。

### 1.2 识别与回传：三个信息源

被动越界**不会自动上报**——程序只会收到 access denied。agent 要拿到"具体需要授权哪个路径"，有三条途径：

**途径 A：预检（推荐，体验最好）**

agent 框架在把工具调用下发给沙箱**之前**，解析命令里的路径，对照策略白名单：

- 命中 `write` / `read` → 直接执行；
- 不在白名单 → 先走授权流程（问用户 / 查 `allow_escalation`），同意后再执行。

好处是"跑一半才失败"不会发生，用户一次授权，整个命令直接通过。

**途径 B：主动提权（执行层权威，`aisbx escalate`）**

沙箱内的程序或包装脚本显式调用：

```text
aisbx escalate -p task.policy.json --path /etc/foo.json --access read
```

客户端（Windows `win/broker.rs::escalate_client` / Unix `unix/broker.rs::escalate_client`）
通过**本任务专属**的控制通道连接宿主 broker：

| | 通道 | 隔离依据 |
|---|---|---|
| Windows | 命名管道 `\\.\pipe\aisbx-<task>` | DACL **只含本任务的 package SID** |
| Unix | UDS `$TMPDIR/aisbx-<task>/esc.sock` | 目录权限 `0700` + 随机任务名 |

两者都保证：沙箱外进程打不开、其他任务的沙箱也打不开 → 授权请求不可能被冒名或串任务。

**途径 C：自动感知（无需程序配合，程序零改动）**

前两条途径都要求「程序或包装脚本主动上报」。但真实场景里大量越界是**程序运行中自己算出来的路径**
（拼接出来的临时文件、遍历出来的目录、配置里读出的位置），程序根本不知道会越界。

本项目提供两条**程序零配合**的感知通道：

| 通道 | 平台 | 来源 | 路径精度 | 归属 |
|---|---|---|---|---|
| **L2 内核日志** | macOS | Seatbelt violation 日志（`com.apple.sandbox.reporting`） | `exact`（内核自带完整路径） | 两级判定：已知 PID 集合 → 进程组反查 |
| **L1 stderr 自报** | 三平台 | 被跑程序自己的错误消息 | `reported`（程序自称，可伪造） | 确定（stderr 来自本次执行） |
| **L3 代理必经点** | 三平台 | 代理的 CONNECT 报文 | `exact`（协议自带） | 确定 |

要点：

- **内核只回 `EACCES`/`ERROR_ACCESS_DENIED`，不含路径**——路径要么由内核日志给出（L2），
  要么由程序自己拼进错误消息（L1）。所以 L1 的覆盖率**取决于程序生态**：
  `sh` / `touch` / `python3` 都会带路径，Rust/Go/C 直接抛 `errno` 的则不带（实测）。
- **L1 的路径可被程序伪造，但伪造不构成越权**：授权对象与被授权对象是同一个路径，
  程序撒谎也拿不到超出用户批准的权限（详见 [docs/08](08-运行时感知通道调研.md) §6.2）。
- **L2 必须做归属判定**：同一个日志流里混着同机其它应用的违规（实测捞到 Chrome、
  `wifip2pd`）。未能归属的条目**只进审计、不驱动授权**，否则会去要用户授权无关路径。
- macOS 侧还有个坑：日志上报的是**真正执行违规的那个进程**的 PID，可比入口深 3 层，
  只按入口 PID 过滤会全漏——故采用「已知 PID 集合 + 进程组反查」两级判定。

broker 裁决顺序（`decide_file`，fail-closed）：

```text
1. deny_escalation 黑名单命中？  → 拒绝（不进用户提示，连问都不问）
2. escalation 模式：
   - prompt：弹到宿主终端问用户；stdin 非 TTY 时 fail-closed 拒绝
   - auto：查 allow_escalation 前缀表，命中自动授权
   - deny：一律拒绝
3. 同意 → 按【该具体路径】落 ACL（目录带 OI/CI 子树继承，文件单挂），
   后续真实 syscall 直接放行；拒绝 → 返回原因
```

应答契约（agent 解析这个）：

```json
{"granted": true,  "reason": "已按具体路径授予 ACL"}
{"granted": false, "reason": "路径在不可授权黑名单内"}
{"granted": false, "reason": "授权被拒绝"}
```

退出码：授权成功 `0`，失败 `1`。

**注意 `prompt` 模式与 agent 的天然冲突**：agent 框架接管 stdin 后宿主通常无 TTY，prompt 会**自动 fail-closed 拒绝**（这是有意设计，防止无人值守时静默放行）。无人值守场景用下面的 **token 授权闭环（§1.5）**或 `auto` 预授权。

### 1.3 Token 授权闭环：无头 agent 运行中授权的完整链路

`auto` 模式只认**启动时固化**的 `allow_escalation` 表（broker 持有策略快照，改文件不热生效），无头 agent 在运行中拿到用户同意后没有通道把它传进沙箱——这就是 token 机制补齐的缺口。链路分两条管道：

```text
┌─────────────────────────── 宿主（信任边界）───────────────────────────┐
│  agent 框架 ──用户同意──▶ aisbx authorize                            │
│      │                     │ ① issue 请求                            │
│      │                     ▼                                         │
│      │              [控制管道 \\.\pipe\aisbx-<task>-ctl]              │
│      │              DACL=SYSTEM/BA/属主,沙箱打不开                    │
│      │                     │ ② 生成一次性 token(128 位,TTL≤1h,单次消费) │
│      │                     ▼                                         │
│      ◀──{token}────────── broker 内存 token 表                        │
│      │                                                               │
│      │ ③ 把 token 传进沙箱(任务输入/环境变量/workspace 文件均可)         │
└──────┼────────────────────────────────────────────────────────────────┘
       ▼
  沙箱内: aisbx escalate -p ... --path C:\X --access write --token <tok>
       │ ④ 消费 token(校验:未过期/路径匹配/access 满足/一次性)
       ▼
  [提权管道 \\.\pipe\aisbx-<task>]  DACL=package SID
       │ ⑤ broker 按 token 里的路径落 ACL → 后续真实 syscall 放行
       ▼
  {"granted": true, "reason": "已按授权 token 授予 ACL(具体路径)"}
```

命令序列（可复制的最小闭环）：

```bash
# ── 宿主侧 ─────────────────────────────────────────────────────
# agent 检测到越界(预检或审计 deny 行),向用户展示:
#   "沙箱请求写入 C:\ProgramData\mydata\result.bin" → 用户同意
aisbx authorize -p task.policy.json \
    --path "C:\ProgramData\mydata\result.bin" --access write --ttl-seconds 300
# 输出: {"granted":true,"token":"a3f9...c41b","path":"...","access":"write","expires_in":300}

# ── 沙箱侧(token 经任务输入传入) ────────────────────────────────
aisbx escalate -p task.policy.json \
    --path "C:\ProgramData\mydata\result.bin" --access write \
    --token a3f9...c41b
# {"granted":true,"reason":"已按授权 token 授予 ACL(具体路径)"}
# 之后沙箱内对该路径的真实读写直接放行,无需再提权

# 沙箱内也可以用文件传递 token(避免长串进命令行/日志):
aisbx escalate -p task.policy.json --path ... --access write --token-file C:\agent\workspace\grant.txt
```

**安全性质**（每条都对应实现）：

| 性质 | 机制 |
|---|---|
| 沙箱不能自己签发 token | 控制管道 DACL=`SY/BA/属主(S-1-3-4)`，无 package SID ACE——AppContainer 附加检查使沙箱进程**即使与宿主同用户**也打不开该管道 |
| token 不可重放 | 一次性，消费即从内存删除（`redeem_token` 先命中后 remove） |
| token 不可挪用 | 签发时绑定 path+access；消费时校验请求路径须落在 token 路径之内（目录 token 覆盖子树）、`write` token 可满足 `read` 请求（Modify 蕴含读），反向不行 |
| token 有时效 | TTL 默认 300s，夹取 1..3600s，签发时顺手清理过期项 |
| token 不能越过黑名单 | `deny_escalation` 检查在 token 消费**之前**，黑名单语义=不可授权 |
| 全程留痕 | `token.issued`（控制侧）/ `token.redeemed` / `token.reject`（消费侧）均落审计 JSONL，token.issued 是复核"agent 是否真的问过用户"的锚点 |

token 的生成用 OS 熵种子的 SipHash 实例（128 位随机）——通道是本机命名管道，强度足够；若未来开放跨机签发，应换 `BCryptGenRandom`。

**途径 C：失败后补偿（兜底）**

程序自己 open 失败时，包装脚本捕获错误后调 escalate——escalate 应答里的 `path` 就是**规范化后、实际被请求的具体路径**（大小写归一、`/` 归一为 `\`、前缀匹配判断），把它透传给 agent，agent 即知道该向用户请求哪个授权。

### 1.4 审计日志：agent 的结构化回传通道

策略里配置 `broker.audit_log` 后，每次裁决落一行 JSONL（`win/audit.rs`）：

```json
{"event":"escalation.grant","op":"file","path":"C:\\ProgramData\\mydata\\x.bin","access":"read","requested_by":{"pid":1234,"exe":"C:\\agent\\workspace\\task-42\\tool.exe"}}
{"event":"escalation.deny","op":"file","path":"C:\\ProgramData\\ssh\\config","access":"write","reason":"deny_escalation","requested_by":{...}}
```

agent 框架 tail 这个文件即可：`escalation.deny` 行的 `path` 字段就是"需要向用户展示的越界对象"，`reason` 区分「黑名单不可授权」（不值得再问用户）与「用户拒绝」（用户已表态）。`requested_by` 携带发起进程的 pid 与 exe，便于归因到具体工具调用。

### 1.5 agent 框架集成示例（Python 伪代码，完整闭环）

```python
POLICY_FILE = "task.policy.json"

def run_tool(cmd: list[str], task):
    # ① 预检：解析命令中的路径，静态对照白名单
    for p in extract_paths(cmd):
        if not whitelisted(p, task.policy):
            # ② 识别到越界 → 问用户 → 宿主侧签发 token
            if not ask_user(f"沙箱外路径需要授权: {p}"):
                raise ToolBlocked(path=p)
            out = host_run(["aisbx", "authorize", "-p", POLICY_FILE,
                            "--path", p, "--access", "write", "--ttl-seconds", "300"])
            token = json.loads(out.stdout)["token"]

            # ③ 把 token 传进沙箱(workspace 文件 / 任务输入均可)
            task.send_input({"grant_token": token})

    # ④ 执行(沙箱内包装脚本消费 token,见下方 escalate_shell)
    r = host_run(["aisbx", "run", "-p", POLICY_FILE, "--json", "--", *cmd])

    # ⑤ 兜底：从审计日志捞本次任务新增的 deny/token 行
    for line in tail_audit(since=r.start_ts):
        if line["event"] == "escalation.deny" and line["op"] == "file":
            report_to_agent(f"访问 {line['path']} 被拒（{line['reason']}），"
                            f"如需继续请向用户申请该路径授权后签发 token")
        if line["event"] == "token.issued":
            record_consent_evidence(line)   # 授权决策留痕

# 沙箱内包装脚本(bat/ps1):失败自动带 token 重试
#   mytool.exe C:\ProgramData\mydata\out.bin
#   if %errorlevel%==5 (  rem ERROR_ACCESS_DENIED
#     aisbx escalate -p task.policy.json --path C:\ProgramData\mydata ^
#         --access write --token-file %WORKSPACE%\grant.txt
#     mytool.exe C:\ProgramData\mydata\out.bin
#   )
```

### 1.6 统一闭环：`aisbx status` 契约 + 授权后重跑

三个平台的**对外契约完全一致**，agent 一套代码即可接入。

**① 启动（后台）**

```bash
aisbx run -p task.policy.json --json -- <命令> [参数...]
```

`--json` 事件流：`spawned` / `exit` / `retry` / `violation` / `violation.captured` /
`violation.unattributed` / `proxy.deny` / `net.grant` / `violation.capture.miss`。

**② 轮询待授权项**

```bash
aisbx status -p task.policy.json
```

```json
{
  "backend": "unix",
  "attempt": 1,
  "retries": 0,
  "needs_approval": true,
  "pending": [
    {"kind": "file", "path": "/x/y.txt", "access": "write", "host": "", "port": 0,
     "source": "stderr-selfreport", "precision": "reported", "attributed": true}
  ],
  "granted_paths": [],
  "granted_nets": [],
  "violations_total": 1
}
```

`pending[]` 给的是**具体路径/主机**（不是数量）——agent 要拿它去问用户
「允许写 /x/y 吗」，只给个数没法问。

**③ 呈现给用户**：两个正交标注必须一起给

| `precision` | 建议话术 |
|---|---|
| `exact` | 「内核确认程序需要访问 /x/y」 |
| `reported` | 「程序声称需要访问 /x/y（路径由程序自报）」 |

| `attributed` | 怎么处理 |
|---|---|
| `true` | 正常走授权流程 |
| `false` | **不要据此授权**——多半是同机其它进程（这类条目只进审计，压根不会出现在 `pending` 里） |

**④ 用户同意后签发**

```bash
aisbx authorize -p task.policy.json --path /x/y --access write
```

- 授权只进**本次任务**的内存清单，不写回基线策略文件；
- 必须存在**真实发生过的**拒绝记录才允许签发（防凭空放行一个从未被拒的目标）；
- 授权路径若尚不存在，Windows 侧只对父目录授 `(AD)`（仅可新建），**不授 Modify**
  ——否则「同意创建这一个文件」实际会变成「可以改/删该目录下所有文件」。

**⑤ 自动重跑**

launcher 检测到授权 → 把该路径并入**策略快照** → 重跑（≤3 轮，每轮最多等 20s）。
只等「需要用户授权」的拒绝；黑名单/策略拒绝直接退出，不浪费用户时间。

**⑥ 收尾**：从 `--json` 事件流读 `exit.code`；出现 `retry` 事件即说明发生过重跑。

## 2. 场景二：网络访问越界 → 识别 → 授权回传

### 2.1 默认行为：仅回环，外网零 capability

`network.loopback: true`（默认）时，宿主用 `CheckNetIsolation LoopbackExempt` 给本任务 package SID 加回环例外（`win/loopback.rs`）——沙箱内进程可以连 `127.0.0.1` 任意端口（对接本地服务、连 broker 都靠它）。

`network.internet: false`（默认）时，LowBox token **不注入** `S-1-15-3-1`（internetClient）与 `S-1-15-3-3`（privateNetwork）capability（`run.rs` 第 44~50 行）。这是内核级判决：任何非回环的 `connect`/`WSAConnect`、DNS 解析出站流量都会直接失败，程序表现为网络不可达/拒绝类错误（常见 `WSAEHOSTUNREACH`）。

### 2.2 识别：与文件不同，判决信息要主动上报

capability 拒绝发生在内核，但**不会告诉任何人"目标地址是什么"**——失败的 connect 只留下一个错误码。要让 agent 拿到具体 host/ip/port，越界程序（或其包装脚本）必须向 broker 上报：

管道协议（单行 JSON，与文件提权同一管道）：

```json
{"op":"net","host":"api.github.com","ip":"140.82.121.6","port":443,
 "requested_by":{"pid":1234,"exe":"C:\\agent\\workspace\\task-42\\tool.exe"}}
```

> **现状边界（务必注意）**：broker 服务端已支持裁决 `op:"net"`，但 **CLI 尚未封装 `aisbx escalate --op net` 子命令**——当前只有 `file` 提权入口（见 `main.rs::cmd_escalate`）。沙箱内程序需要自行连管道发送上述 JSON（协议见上），或等 v0.2 补齐 CLI。宿主侧语言（如包装脚本跑在沙箱外时）直接写审计通道不适用，必须走管道才能被 DACL 验证为本沙箱进程树。

### 2.3 broker 对 net 请求的裁决：fail-closed + 明确指引

`decide_net` 的当前行为：

- `network.internet: true` → 直接放行应答（整域已开，无需逐主机）；
- 否则 → **拒绝**，审计落一行含 `host` / `ip` / `port` 的 `escalation.deny`，应答 reason 为：

```json
{"granted": false,
 "reason": "外网默认拒绝;按主机放行需 WFP 规则(见设计文档路线图),可改策略 network.internet 或改用代理"}
```

也就是说：**识别是完整的**（具体地址进了审计日志），但**运行时按主机的精确放行暂不可用**——运行中的沙箱无法补挂网络规则。

### 2.4 三条出路（按推荐排序）

| 出路 | 粒度 | 成本 | 适用 |
|---|---|---|---|
| **② 宿主侧代理（推荐）** | **按域名/IP 精确** | 中：宿主跑一个回环代理（监听 `127.0.0.1:8888`），沙箱内进程设 `HTTPS_PROXY` 指向它；代理持有对外网络，在宿主侧做 PEP——逐请求判域名，未授权弹用户 | agent 框架默认方案。**最贴近"具体地址授权"语义**：识别（上游见到的目标地址）与放行（代理白名单）都在宿主侧可控 |
| ① 整域放开 | 粗（全部外网） | 零：策略 `network.internet: true`，任务重启生效 | 可信度高的构建/依赖拉取场景；或作为代理方案的降级 |
| ③ WFP 按主机放行 | 精确（IP/端口级内核规则） | 高：WFP 需管理员权限，与"无需管理员"的设计约束冲突 | 路线图 v0.2，见 docs/02 |

代理方案下"识别→授权"闭环为：沙箱内 connect 回环代理（默认允许）→ 代理向宿主/框架询问该域名是否放行 → 未授权则上报目标地址（域名+端口）给 agent → 用户同意后加入代理白名单。这与 §1 的文件闭环语义完全对称。

## 3. 场景三：资源超限会被发现吗（CPU / 内存 / 磁盘 / 进程数）

限制全部挂在 Job Object 上（`win/job.rs`），子进程强制继承（未开 breakaway），bash→gcc→curl 全树同预算。逐维度看"超限表现"与"可发现性"：

### 3.1 逐维度行为表

| 维度 | 策略字段 | 内核机制 | 超限表现 | agent 能否发现 |
|---|---|---|---|---|
| 单进程内存 | `memory_mb_per_process` | `JOB_OBJECT_LIMIT_PROCESS_MEMORY` | 该进程 commit 超限时新分配失败，程序通常以内存错误崩溃退出 | ✅ **退出码可观测**（`run --json` 的 `exit` 事件 / wait 返回码） |
| 全任务内存 | `memory_mb_total` | `JOB_OBJECT_LIMIT_JOB_MEMORY` | **所有进程合计** commit 超限时新分配失败（既有提交不受影响），常见表现为新进程/新线程/新缓冲区创建失败 | ✅ 程序以错误退出，退出码可观测 |
| CPU | `cpu_percent`（1..=100） | `CPU_RATE_CONTROL_HARD_CAP`（万分比硬顶，50% = 5000） | **节流而非终止**：按 CPU 时间配额调度，程序收不到任何错误，只是变慢 | ⚠️ **运行中不可发现**——这是 hard cap 语义，见 3.2 |
| 进程数 | `active_processes` | `ActiveProcessLimit` | fork 炸弹在到达上限时 `CreateProcess` 直接失败，攻击者在第 N+1 个进程处停下 | ✅ 程序收到进程创建错误（错误码可通过 GetLastError 查看） |
| 磁盘 IOPS | `max_iops` | —（**未实现**，job.rs 中已有错误提示注明） | 不拦截、不上报 | ❌ 当前不限制也不可发现，见现状边界 |
| 兜底 | — | `KILL_ON_JOB_CLOSE` | 宿主（`aisbx run` 进程）退出/被杀 → 全树立即终止 | ✅ 框架崩溃不留孤儿进程（这是可用性保证，不是检测） |

### 3.2 CPU 的特殊性：节流 ≠ 信号

`HARD_CAP` 的语义是**把整棵进程树的 CPU 时间占比压在配额内**（如 50%），超了就排队等下个调度周期。因此：

- 程序**永远不会**因为 CPU 超限而失败——它只是变慢。如果 agent 需要知道"程序是不是顶满了 CPU 配额"，当前有两个途径：
  1. **宿主侧采样**：框架定期读任务进程树的 CPU 时间（如 Windows `GetProcessTimes` / 任务管理器等价物），对照 `cpu_percent × 墙钟时间` 估算饱和度；
  2. **Job accounting 接口**：内核在 Job 上维护完整的 IO/CPU/内存峰值计数器（`QueryInformationJobObject` + `JobObjectBasicAndIoAccountingInformation`），**接口存在但当前代码未输出**——这是最自然的"任务结束后出具资源账单"通道，列入 v0.2（见 §4）。
- CPU 节流的"发现"因此定位为**观测问题而非拦截问题**：想要"超 CPU 就杀"的语义，框架应配合超时机制（如宿主 wait + deadline，超时后终止任务），而不是等内核报错。

### 3.3 agent 拿到什么（当前实现的可观测面）

```bash
aisbx run -p task.policy.json --json -- cmd /c build.bat
```

`--json` 事件流（stdout，逐行 JSON）：

```json
{"event":"sid","sid":"S-1-15-3-4096-..."}     # 本任务 package SID
{"event":"network","loopback":true}            # 网络例外已挂
{"event":"spawned","cmd":["cmd","/c","build.bat"]}
{"event":"exit","code":3221225725}             # 主进程退出码(内存崩溃时是异常大数,如 0xC0000005/0xC00000FD)
```

内存超限的典型信号：子进程退出码为异常码（`0xC0000005` access violation / `0xC00000FD` stack overflow / CRT abort 形态），且审计/运行日志显示任务在资源敏感操作处终止。**磁盘与 CPU 的运行中水位当前没有输出通道**——这是现状，不是设计遗漏。

### 3.4 集成建议

- **必配**：`memory_mb_per_process` + `memory_mb_total` + `active_processes`——这三项超限必然产生可观测的程序错误，闭环成立。
- **CPU**：把 `cpu_percent` 当"保险丝"而非"检测器"，防失控吃满机器；业务层的"超时/超算力终止"由框架 deadline 承担。
- **磁盘**：v0.2 前依赖宿主侧配额（如对 workspace 目录挂 NTFS quota）或接受不设防。
- **任务结算**：等 v0.2 的 Job accounting 输出后，每次任务结束自动产出一行资源账单（CPU 时间 / IO 字节 / 峰值内存 / 存活进程数），agent 可用于回填判断"这个任务是否顶着上限跑"。

## 4. 现状边界（如实列出，避免误依赖）

| 能力 | 现状 |
|---|---|
| 文件越界的**自动**感知（程序零配合） | ✅ **macOS**：内核 Seatbelt violation 日志（`exact`，「已知 PID 集合 + 进程组反查」两级归属）；**Linux / Windows**：stderr 自报（`reported`，归属确定）。未能归属的条目**只进审计、不驱动授权**（见 §1.2 途径 C） |
| Linux 的**内核侧**精确路径（`exact`） | ❌ 未实现。Landlock 6.15 audit 需内核 ≥6.15、auditd 需 root、seccomp `USER_NOTIF` 成本过高——三条路当前**都无法验证**，故不盲写（见 [docs/08](08-运行时感知通道调研.md) §6.1，附触发条件） |
| Windows 的**内核侧**精确路径（`exact`） | ❌ 未实现（minifilter 需 EV 签名驱动；Object Access Audit 需管理员 + SACL，事后通道） |
| 宿主侧运行中授权（token 闭环） | ✅ 三平台已实现：一次性 / TTL / 路径绑定 / 黑名单前置；且 **launcher 会等授权并自动重跑**（≤3 轮）——Windows 的 `launcher_retry` 已由 `unavailable` 改为 `full` |
| 网络按主机/域名的**运行时**精确放行 | ✅ 已实现（三平台）：强制代理 + CONNECT 报文自带目标 + 代理侧授权，**运行中放行、命令不重跑**。仅覆盖遵守代理环境变量的客户端（裸 socket / 忽略 `HTTP_PROXY` 的客户端仍由内核默认拒绝） |
| `aisbx escalate` CLI 的 `net` 子命令 | ✅ 已封装（三平台） |
| 磁盘 IOPS 限制（`max_iops`） | ❌ 策略字段已定义未实现，超限不拦截 |
| 资源运行中水位 / 任务结束资源账单 | ❌ 未输出（Job accounting 接口现成，列为 v0.2） |
| macOS 资源硬限制（cgroups 等价物） | ❌ 无等价内核机制（如实标 `unavailable`） |
| prompt 模式在无 TTY 环境 | ✅ 不再直接拒绝：置 `needs-approval` 交给宿主授权通道（Windows 侧已改；Unix 侧同一契约）。无人值守场景仍推荐 `auto` 预授权或 token 闭环 |
| 授权粒度（Windows） | 授权「创建某文件」时只对父目录授 `(AD)`（仅可新建），**不授 Modify**——避免授权范围悄悄扩大到整个目录 |
| Windows 真机回归 | ⚠️ T11–T13 只做了交叉编译，**尚未在真实 Windows 上跑过**（本机无 Windows 内核），由 CI `windows-smoke` 承担 |

设计层面的完整取舍（为什么 hook/ETW 不做被动上报、为什么 WFP 缓一缓）见 [docs/02-设计与实现.md](02-设计与实现.md)。

## 5. 三个场景的推荐接入姿势（速查）

```text
文件：  (可选)预检白名单 → 沙箱内跑 → 感知到【具体路径】
        (L2 内核日志 exact / L1 stderr 自报 reported)
        → aisbx status 取 pending[] → 问用户(带 precision/attributed 标注)
        → aisbx authorize 签发 → launcher 自动以更宽的快照重跑(≤3 轮)
        兜底：审计 JSONL 的 violation.captured / violation.unattributed 回传 agent

网络：  默认仅回环 → 出站必经宿主代理 → 代理侧按域名问用户
        → 运行中放行(不重跑)
        兜底：net.grant / proxy.deny 审计行回传 agent

资源：  内存/进程数配额必配(超限=可观测错误) + CPU 硬顶当保险丝 + 框架 deadline 管超时
        兜底：run --json 的 exit.code
```

## 6. Windows 版本支持矩阵
